Lesson 14

What to take back to your day job

Most of what made this project trustworthy is a set of habits that work in any language, with or without a proof assistant. This lesson lists them, roughly in order of value, then covers when full verification is worth the cost and where to go next.

Habits that transfer

1. Write the yes/no test for every sentence of the spec

Stage 1 found the NaN threshold bug, the string-compared timestamps, the URL injection and the float rounding problem before any code was written, through careful reading and a few experiments. Keep an ambiguity register: each question the spec doesn't answer, what the current code actually does (run it rather than guessing), and the decision. It found more bugs than anything else in this project, and it needs no tools.

2. Get expected values from somewhere other than the code

A test whose expected value came from running the function under test can't fail. Here, epoch values came from GNU date, text from the PRD's examples, and edge cases from the ambiguity register. A stub answers with a fixed value chosen by the test, never one computed from its input.

3. Functional core, imperative shell, and effects as data

Put the decisions in pure functions, and the I/O in a thin layer that makes no decisions. If you go one step further and have the core return a description of what it wants to do (a Prog, a list of commands, a coroutine that yields requests), you can test the whole program against scripted worlds, with no mocking framework, in microseconds, and the shell becomes small enough to read in one sitting. The pattern has a name worth searching for: "functional core, imperative shell".

4. Mutation-test your checks

Plant a plausible bug and confirm something fails. Do it for tests, for CI gates, for linters, for audit scripts, for monitoring alerts. Whenever a check asserts that something didn't happen, add a positive control showing the same check notices when it does. The vacuous glob in Lesson 10 is the most common real-world failure mode of test suites, and the cheapest to prevent.

5. Name your trusted base, and contract-test your mocks

Write down what your guarantees depend on but don't check, such as the database's isolation level, the HTTP client's timeout behavior, or the clock. For each mock, run the same assertions against the real dependency once, so the mock can't drift from reality without something failing.

6. Use exact arithmetic for anything that makes a decision

Thresholds, money, quotas: compare exact values (integers, or decimals as integer plus scale), never binary floating point. Round once, at display time, with a stated rule.

7. Test finite domains exhaustively

hour12 has 24 inputs; the calendar proof checked 400 era-years. If a function's domain is small, or can be reduced to a small set of boundary cases plus a monotonicity argument, test every case. For a function like hour12, a unit test that loops over all 24 hours is as good as a proof.

8. Use property-based testing

Property-based testing sits between a few examples and every input: it checks a property against thousands of random inputs. Writing the property is exactly the spec-writing skill from Lesson 6: "parse(render(x)) == x", "the result is within ½", "the chosen reading is no earlier than any other". For C++, RapidCheck does this in the QuickCheck style. It won't prove anything, but it finds a lot of bugs for the effort.

When full verification is worth it

The proofs here are four times the size of the code they cover, and they took the most effort of any stage. That's worth paying when being wrong is expensive and the logic is intricate enough that testing can't cover it: parsers of untrusted input, crypto, consensus and replication protocols, schedulers, financial calculations, safety interlocks. It isn't worth paying for code whose correctness is mostly "does it look right", such as UI layout or report formatting. This project deliberately didn't verify its report text, which is a template checked by tests. The proofs cover the part that decides whether to send an alert.

Tools, if you want to go further

ToolGood for
CBMCBounded model checking of C and C++: checks assertions, overflow and memory safety for every input up to a bound, and gives a counterexample trace. The lowest-friction entry point for a C++ codebase.
Frama-CDeductive verification of C: annotate functions with contracts, and automatic provers discharge them.
DafnyA verification-aware language: pre/postconditions and loop invariants, proved automatically where possible. Gentler than Lean.
TLA+Designs of concurrent and distributed systems. You verify a model of the design rather than the code, which finds design bugs before any code is written.
Lean 4What this project uses: full proofs about real, compiled code. The most expressive and the most work.

Where this project could go next

Each of these is a real exercise, roughly in order of difficulty:

  1. Strengthen parseArgs_dup to cover an option repeated anywhere in the argument list, in either form (Lesson 6). Start by writing just the statement.
  2. Prove that DayCount pins down a unique function on valid dates, turning the doc comment's claim into a theorem.
  3. Give leanchecker a negative control, so its exit code of 0 means something (Lesson 10).
  4. Add alert de-duplication across cron runs, which the PRD lists as a non-goal. The tool would have to remember state between runs, and the interesting properties ("never two alerts for the same high-water event", "never zero alerts for a new one") are about sequences of runs. That's a natural fit for TLA+ before any code is written.
  5. Write and verify a small JSON parser, moving Lean.Json.parse out of the trusted base (and shrinking the binary).

Summary

  1. Most bugs are found by stating precisely what "correct" means; do that first, in writing.
  2. A spec that restates the implementation proves nothing, and no tool will tell you that yours does. Write each one in a different style from the code, and have someone else check.
  3. Describing I/O as data lets you state, and prove, properties over every possible environment.
  4. Proofs move risk into a small, named trusted base; aim your tests there.
  5. Every check, including the ones that check the checks, should be shown to fail at least once.
