Lesson 3 · Stage 1

Requirements: what the prose left unspecified

Stage 1 takes each sentence of the PRD and tries to write a yes/no test for it. Each time that isn't possible, the PRD has left a question unanswered. This was the cheapest way of finding bugs in the whole project.

Stage 1 commit 33d8858 what changed since stage-0 docs/01-requirements.md

The method

The method is mechanical:

  1. Atomize. Split every sentence into claims that are individually true or false. "Print the site name, the level to two decimal places, when it was observed and how long ago that was" is at least four requirements.
  2. Try to write the test. For each claim, write down an exact input and the exact expected output. When you can't, because the prose doesn't say, you've found an ambiguity.
  3. Decide, and write the decision down. Every ambiguity gets a resolution and a reason. By the end of this stage, no question is left open.
  4. Tag how each requirement will be checked. This is the first point at which anyone asks "which parts can we actually prove?"

The output is docs/01-requirements.md: an ambiguity register (A1–A21) and a numbered requirements list (R1–R71).

Checking claims against the original by running it

Wherever the PRD was ambiguous, the register records what the Python original actually did. Each of those claims was checked by running Python, not by reading the code. Here are four of the findings.

Finding 1: --threshold nan silently disables alerting

The original declares the option like this:

p.add_argument("--threshold", type=float,

and decides to alert with:

if args.threshold is not None and level >= args.threshold:

Python's float() accepts the string "nan". And every comparison with NaN is false:

$ python3 -c 'x = float("nan"); print(677.58 >= x, 700 >= x)'
False False

So lake-level --threshold nan runs, prints the report, never alerts, and exits 0, on every run. A typo in a cron job could produce exactly this. It's a direct violation of the PRD's "never silently fail to alert", and no amount of testing the alert path with sensible thresholds would find it. It was found by asking "what is a valid threshold?" and trying to write the answer down.

Decision (A6): a threshold is exactly -?[0-9]+(\.[0-9]+)?. Anything else is a usage error. (float() also accepts inf, 1e3, " 685 " and 6_85; all now rejected.)

Finding 2: "most recent" compared timestamp strings

return max(records, key=lambda r: r["dateTime"])

That compares the text, alphabetically. It gives the right answer only as long as every timestamp has the same format and the same time zone. It works today because the API happens to send them all in UTC with a Z. But:

$ python3 -c 'print(max(["2026-10-20T04:00:00-05:00", "2026-10-20T08:00:00Z"]))'
2026-10-20T08:00:00Z

04:00-05:00 is 09:00 UTC, the later moment, but it loses. Decision (A1): order readings by the instant they denote. Among readings tied for the latest instant, pick the first in the list. (A2 then accepts only the canonical UTC format, so the string-order bug can't come back.)

Finding 3: user input pasted into URLs

--site, --type and --ntfy-topic were pasted into URLs unchecked. --site '3963?x=1' changes the query string; --ntfy-topic a/b posts somewhere else. Decision (A17): site is [0-9]{1,9}, type is [a-z]{1,32}, topic is ntfy's own topic rule, [-_A-Za-z0-9]{1,64} (which was checked against ntfy's server source, not guessed).

Finding 4: corrupt older records are never read

The original reads value1 and parses the timestamp only for the newest record. A null or missing value1 there crashes it with a traceback. The same defect in any other record is never looked at: the original prints its report, sends an alert if the level is high, and exits 0 without mentioning the corrupt data. Decision (A7): if any record is malformed, the whole response is rejected with an error.

And a smaller one: binary floating point

$ python3 -c 'print(f"{2.675:.2f}", f"{0.125:.2f}", "%.20f" % 677.58)'
2.67 0.12 677.58000000000004092726

The PRD says "never report a wrong level", but a binary double can't even hold 677.58. Decisions A3 and A4: levels are exact decimals (the rational number written in the JSON), and rounding is to the nearest, ties away from zero. So 2.675 becomes 2.68.

C++ analogy

All of these are "the default did something reasonable-looking". std::stod("nan") also succeeds; std::max on std::string also compares text; printf("%.2f", 2.675) also prints 2.67. Nothing here is specific to Python. The bugs come from never having written down what the right answer is.

Writing requirements a stranger could check

After the register, the requirements are written so that a stranger, given one run of the program, could say whether it complied. Two examples, verbatim:

R50 An alert shall be attempted if and only if a threshold was given, the response is valid, and level ≥ threshold exactly.

R62 If the run is not a success, the exit status shall be non-zero. In particular, there shall be no outcome in which a threshold was given, the level was ≥ threshold, no alert was delivered, and the exit status is 0.

Notice "if and only if" in R50. The PRD only said when to alert. It didn't say "and never otherwise", which is just as important: an alarm that fires all the time is useless.

Tagging: which parts can be proved?

Each requirement gets a tag saying how it will be checked:

TagMeaningExamples
Proveda machine-checked theorem over all inputsrounding, calendar, alert decision, exit codes
Testedspecific runs checked automaticallythe 30 s timeout, run time under 5 s
Inspecteda human reads a small piece of trusted code"the request we built is the one actually sent"
Assumedrelied on, not checked; written downthe JSON parser, the time-zone database, the clock

The tags already shape the architecture. Most requirements are P, so they must live in code with no I/O at all, because you can't prove things about a network. The I items must live in code small enough to read in one sitting. That's Lesson 4's "functional core, imperative shell".

Try it

Take a feature spec from your own work, a ticket or a design doc. Pick one paragraph and do steps 1–3 on it. Count the ambiguities. Then check what your code actually does for each one by running it, not by reading it.
