Lesson 8 · Stage 5

Anatomy of a proof

This lesson walks through the most important theorem in the project, "it never silently fails to alert", one tactic at a time, with the goal Lean displays at each step. Then it runs the same proof against a deliberately broken implementation.

The vocabulary

The theorem is stated in terms of a few definitions in the proofs file. They're the vocabulary of "what the world did":

/-- The world returned a successful, valid response for `cfg`, decoding to `S`, `R`. -/
def Fetched (cfg : Cfg) (w : World) (S : Site) (R : Reading) : Prop :=
  ∃ status body, w.get (fetchReq cfg) = .response status body ∧ ok2xx status ∧
    decodeBody (siteNum cfg.site) body = .ok (S, R)

/-- The alert condition (R50): a threshold was given and the exact level meets it. -/
def ShouldAlert (cfg : Cfg) (R : Reading) : Prop :=
  ∃ th, cfg.threshold = some th ∧ th.value.val ≤ R.level.val

Notice that ShouldAlert compares .val, the exact rational values from the spec, not the implementation's Dec.le. So somewhere the proof has to use the fact that Dec.le is correct. That's how proofs compose: the whole-program theorem relies on the decimal theorem.

Delivered w q, from Lesson 5, means "the world answered POST q with a 2xx status".

The plan, in English

Before any Lean, here's the argument a person would give:

  1. Every run with a valid command line has one of two shapes. Either nothing valid was fetched, in which case it printed one error and exited 1, or it fetched something, printed the report, and then did whatever the alert step (finish) does. (This is a separate lemma, run_ok_cases.)
  2. We're told something valid was fetched, so it's the second shape.
  3. The world's answer to the GET is fixed, so what was fetched is the reading we were told about. (Another small lemma: Fetched.unique.)
  4. So the program's exit status is finish's exit status, and we're told it's 0.
  5. finish exits 0 with an alert due only if the POST came back 2xx. (Lemma: finish_exit0.)

The Lean proof is that argument, nearly line for line.

The proof

/-- **R62: "it should never silently fail to alert."** If the run exits 0 and
the alert condition held, the alert was delivered. -/
theorem never_silently_fails (argv : List String) (w : World) (cfg : Cfg) (S : Site) (R : Reading)
    (h : parseArgs argv = .ok cfg) (hf : Fetched cfg w S R) (ha : ShouldAlert cfg R)
    (h0 : exitCode argv w = 0) :
    Delivered w (alertReq cfg S R) := by
  unfold exitCode at h0
  rcases run_ok_cases argv w cfg h with ⟨hn, -⟩ | ⟨S', R', hF, hr⟩
  · exact absurd ⟨S, R, hf⟩ hn
  · obtain ⟨rfl, rfl⟩ := Fetched.unique hF hf
    rw [hr] at h0
    obtain ⟨th, hth, hle⟩ := ha
    exact finish_exit0 cfg S' R' w th hth ((Dec.le_iff _ _).2 hle) h0

Step by step

The goal states below are Lean's real output, captured by inserting trace_state between the tactics of a copy of this proof. Hypotheses are above the line; the goal is after ⊢.

At the start

argv : List String
w : World
cfg : Cfg
S : Site
R : Reading
h : parseArgs argv = ArgResult.ok cfg
hf : Fetched cfg w S R
ha : ShouldAlert cfg R
h0 : exitCode argv w = 0
⊢ Delivered w (alertReq cfg S R)

The parameters became hypotheses. We have to produce evidence of Delivered.

unfold exitCode at h0

h0 : ((main argv).run w).snd = 0

(Only the changed line is shown.) exitCode was shorthand for "the second component of running main in w". Now it's spelled out, so later steps can rewrite inside it.

rcases run_ok_cases argv w cfg h with ⟨hn, -⟩ | ⟨S', R', hF, hr⟩

Use the shape lemma, and split on its "or". This creates two goals, one per shape. The first is the "nothing valid was fetched" case:

case inl
⋮ (as before)
hn : ¬∃ S R, Fetched cfg w S R
⊢ Delivered w (alertReq cfg S R)

Here hn says nothing was fetched, but hf says S and R were. Those contradict each other. exact absurd ⟨S, R, hf⟩ hn says exactly that: "here's a witness that something was fetched, and here's hn denying it; from a contradiction, anything follows". That closes the first goal.

C++ analogy

It's an unreachable branch. In C++ you'd write std::unreachable() and hope. Here you have to prove it's unreachable, and absurd is how you do it: show that two things you hold contradict each other.

The second shape: obtain ⟨rfl, rfl⟩ := Fetched.unique hF hf

In the second case, the shape lemma gives us some fetched S' and R', and an equation hr for the entire run. Fetched.unique says they must be our S and R. Matching its result against rfl ("these are literally equal") makes Lean substitute one for the other everywhere:

case inr
argv : List String
w : World
cfg : Cfg
h : parseArgs argv = ArgResult.ok cfg
h0 : ((main argv).run w).snd = 0
S' : Site
R' : Reading
hF : Fetched cfg w S' R'
hr :
  (main argv).run w =
    (Event.get (fetchReq cfg) :: preReport cfg R' ++
        Event.out (reportFor cfg w S' R') :: ((finish cfg S' R').run w).fst,
      ((finish cfg S' R').run w).snd)
ha : ShouldAlert cfg R'
hf : Fetched cfg w S' R'
⊢ Delivered w (alertReq cfg S' R')

hr is the whole run, written out: the GET, then the zone/clock queries (preReport), then the report, then whatever finish does. The exit status is finish's.

rw [hr] at h0

h0 :
  (Event.get (fetchReq cfg) :: preReport cfg R' ++ Event.out (reportFor cfg w S' R') :: ((finish cfg S' R').run w).fst,
        ((finish cfg S' R').run w).snd).snd =
    0

Rewrite h0 using hr. It now says "the second component of that pair is 0", which Lean can see means ((finish cfg S' R').run w).snd = 0.

obtain ⟨th, hth, hle⟩ := ha

th : Threshold
hth : cfg.threshold = some th
hle : th.value.val ≤ R'.level.val
⊢ Delivered w (alertReq cfg S' R')

Unpack "an alert should be sent" into its parts: the threshold th, the fact that the configuration has it, and the exact comparison.

exact finish_exit0 cfg S' R' w th hth ((Dec.le_iff _ _).2 hle) h0

Call the lemma about finish, handing it everything it needs. One argument is interesting: finish_exit0 is about the code, so it wants Dec.le … = true, but we have hle, a statement about rationals. (Dec.le_iff _ _).2 hle converts one into the other, using the "right-to-left" direction (.2) of the decimal theorem. No goals remain. The theorem is proved.

Where the real work is: finish_exit0

That last step pushed all the substance into a lemma about the alert step:

theorem finish_exit0 (th : Threshold) (hth : cfg.threshold = some th)
    (hle : Dec.le th.value R.level = true) (h0 : ((finish cfg S R).run w).2 = 0) :
    Delivered w (alertReq cfg S R) := by
  simp only [finish, hth, hle, ite_true] at h0
  cases hp : w.post (alertReq cfg S R) with
  | response st =>
    simp only [Prog.run, hp] at h0
    by_cases hs : ok2xx st
    · exact ⟨st, hp, hs⟩
    · simp [Prog.run, hs] at h0
  | failed m => simp [Prog.run, hp] at h0

It's a case analysis on what the world answered to the POST:

  • A 2xx status. Then ⟨st, hp, hs⟩ is literally the evidence Delivered asks for: a status, the fact that the world answered with it, and the fact that it's 2xx.
  • Any other status. simp evaluates the program: in that branch finish exits 1. So h0 becomes 1 = 0, which is false, and a false hypothesis closes any goal.
  • A transport failure. Same: exit 1, so h0 is 1 = 0.

The proof doesn't enumerate status codes. "Any other status" is one case, covering 0, 199, 302, 500 and 4,294,967,296 at once.

What it looks like when the code is wrong

Now plant the bug the whole PRD was worried about. In finish, change the exit status after an HTTP error from 1 to 0:

-          else .err (errLine (sanitize s!"ntfy alert failed: HTTP {st}")) (.done 1)
+          else .err (errLine (sanitize s!"ntfy alert failed: HTTP {st}")) (.done 0)

Every test that doesn't specifically check an HTTP error status would still pass. Here's what lake build says:

Read the stuck goal as a counterexample. The world answered the POST with some status st that is not 2xx (hs). The exit status was 0: h0 has become trivially True, so it's no longer a contradiction. And we're asked to show that the alert was delivered, which is false. Lean is telling you: "here's a situation where your program exits 0 and the alert wasn't delivered". It points at line 136, the "not 2xx" branch.

And because the binary imports the proofs, the broken program doesn't build. You can't ship it by accident.

The rest of the whole-program theorems

All in Proofs/Program.lean, and all for every command line and every world:

TheoremSays
alert_iffan alert is attempted if and only if something valid was fetched and the alert condition holds (R50)
alert_contentthe alert sent is exactly alertReq cfg S R (R51)
report_before_alertin the trace, the report always comes before the POST (R52)
bad_fetch_behaviorif nothing valid was fetched: no output, no alert, exit 1 (R15)
usage_behaviora usage error makes no network request and exits 2 (R3)
only_fetch_getthe only GET is the fetch request (R4)
report_writtenon a good fetch, the report is the only thing written to stdout
stderr_shapeevery stderr write is a one-line Error: message, or the alert notice (R60)
exit_codesthe exit status is 0, 1 or 2, and 2 exactly for usage errors (R61)
succeeds_when_it_shouldthe converse of the headline theorem: a good fetch with no alert needed, or with the alert delivered, exits 0

The last one matters as much as the headline theorem. A program that always exits 1 would satisfy never_silently_fails trivially, because it never exits 0 at all. Proving the converse rules that out.
