Lesson 11

Where is the actual program?

If you browse the repository, you'll find Lean files, Markdown, and some shell and Python under test/, but nothing that looks like the program itself. That's because the Lean files are the program. This lesson shows how they become a native executable, and what happens to the proofs.

The short answer

  • The source is LakeLevel/Impl/*.lean (the logic, about 450 lines) and Main.lean (the I/O, 80 lines). Lean 4 is a general-purpose compiled language, not only a prover.
  • The build is lake build. Lake is Lean's build tool: think CMake and a package manager in one.
  • The binary is .lake/build/bin/lake-level, a native ELF executable. It's not in git for the same reason your build/ directory isn't: .gitignore lists .lake/.
$ file .lake/build/bin/lake-level
.lake/build/bin/lake-level: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 2.6.32, with debug_info, not stripped
$ .lake/build/bin/lake-level --threshold nan
Error: --threshold must be a decimal number like 685 or 680.5: nan
usage: lake-level [--site N] [--type T] [--json] [--threshold FT] [--ntfy-topic TOPIC]
$ echo $?
2

The build file

name = "lake-level"
version = "0.1.0"
defaultTargets = ["LakeLevel", "Tests", "lake-level"]

[[lean_lib]]
name = "LakeLevel"

[[lean_lib]]
name = "Tests"
srcDir = "test"

[[lean_exe]]
name = "lake-level"
root = "Main"
C++ analogy

lean_lib is add_library and lean_exe is add_executable. The LakeLevel library is everything under LakeLevel/: spec, implementation and proofs. Tests is a library that produces nothing useful. Building it runs its #guard and #eval checks, which is its only purpose. The executable's root is Main.lean, whose last line is the equivalent of int main(int argc, char** argv):

def main (args : List String) : IO UInt32 := interp (LakeLevel.main args)

"Build the verified Prog from the arguments, then interpret it with real I/O, and return its exit status." Everything else in the program is reached from that line.

From .lean to a native binary

  1. Elaboration. lean reads the file, works out every type, and runs the tactics, which build proof terms. #guard and #eval commands run here, which is why tests can fail the build.
  2. Kernel check. Every definition and every proof term is checked by the kernel before it's accepted. A proof that doesn't check is a compile error.
  3. Outputs. An .olean file (the compiled module, which other files import) and a .c file (the executable code), both under .lake/build/.
  4. C compilation and linking. The toolchain ships its own clang and ld.lld (look in ~/.elan/toolchains/*/bin/). Lake compiles each .c and links the objects with Lean's runtime and standard libraries.

Read the generated C

The C is readable, if verbose. Here's what select (the fold that keeps the first of the latest readings) became, from .lake/build/ir/LakeLevel/Impl/Select.c after a build (verbatim):

LEAN_EXPORT lean_object* lp_lake_x2dlevel_List_foldl___at___00LakeLevel_select_spec__0(lean_object* v_x_1_, lean_object* v_x_2_){
_start:
{
if (lean_obj_tag(v_x_2_) == 0)
{
lean_inc_ref(v_x_1_);
return v_x_1_;
}
else
{
lean_object* v_head_3_; lean_object* v_tail_4_; lean_object* v_t_5_; lean_object* v_t_6_; uint8_t v___x_7_;
v_head_3_ = lean_ctor_get(v_x_2_, 0);
v_tail_4_ = lean_ctor_get(v_x_2_, 1);
v_t_5_ = lean_ctor_get(v_x_1_, 0);
v_t_6_ = lean_ctor_get(v_head_3_, 0);
v___x_7_ = lean_int_dec_lt(v_t_5_, v_t_6_);
if (v___x_7_ == 0)
{
v_x_2_ = v_tail_4_;
goto _start;
}
else
{
v_x_1_ = v_head_3_;
v_x_2_ = v_tail_4_;
goto _start;
}
}
}
}

Things to notice:

  • lean_obj_tag(v_x_2_) == 0 is "is the list empty?", because constructor number 0 of List is [].
  • lean_ctor_get(v_x_1_, 0) reads field 0 of a Reading, its timestamp t.
  • lean_int_dec_lt is the strict < on arbitrary-precision integers. This one function call is the "first of the tied readings wins" behavior the proof is about. Change it to ≤ in the Lean and this becomes lean_int_dec_le, and a proof breaks (Lesson 10).
  • The recursion became goto _start: a loop. Tail calls are compiled to jumps, so folding a long list doesn't grow the stack.
  • lean_inc_ref and lean_dec are reference counting. Lean's memory management is reference counting (like std::shared_ptr), not a tracing garbage collector.

Where do the proofs go?

They don't go into the binary. A theorem's proof has no run-time behavior; once the kernel has accepted it, there's nothing to execute. You can check by looking for symbols:

$ nm .lake/build/bin/lake-level | grep -c never_silently_fails
0
$ nm .lake/build/bin/lake-level | grep -E 'LakeLevel_(select|decode|main)$'
0000000000b454f0 T lp_lake_x2dlevel_LakeLevel_decode
0000000000b4ba30 T lp_lake_x2dlevel_LakeLevel_main
0000000000b43d10 T lp_lake_x2dlevel_LakeLevel_select

The proofs live in the .olean files, where the audit and other modules can see them. They can be large: Proofs/CalendarLemmas.olean is about 12.7 MB, against 25 KB for Impl/Select.olean. The proof files do produce some C (helper definitions such as yoeOf, and functions Lean generates to support reasoning about pattern matches), but the linker drops it from the binary because nothing calls it.

C++ analogy

Proofs are like static_asserts and concepts: they're checked at compile time and cost nothing at run time. The difference is in what they can say. static_assert checks one constant expression. A theorem checks a claim about every possible input.

Why is the binary 118 MB?

It's large, for a program that does so little:

$ ls -l .lake/build/bin/lake-level
-rwxrwxr-x 1 … 118752352 … .lake/build/bin/lake-level
$ strip -o /tmp/ll .lake/build/bin/lake-level && ls -l /tmp/ll
-rwxrwxr-x 1 … 78928984 … /tmp/ll

About a third is symbols and debug information, which strip removes. The rest is mostly Lean's own libraries, linked statically. The JSON parser this program uses lives in the Lean package, which is the compiler's own library (its static archive, libLean.a, is about 312 MB in this toolchain). The link line includes -lLean -lStd -lInit -lleanrt, plus -lgmp (GMP, for big integers) and -luv. The only shared libraries at run time are the C library's:

$ ldd .lake/build/bin/lake-level
	linux-vdso.so.1
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
	/lib64/ld-linux-x86-64.so.2
	libpthread.so.0 => /lib/x86_64-linux-gnu/libpthread.so.0
	libdl.so.2 => /lib/x86_64-linux-gnu/libdl.so.2
	librt.so.1 => /lib/x86_64-linux-gnu/librt.so.1
	libm.so.6 => /lib/x86_64-linux-gnu/libm.so.6

(Load addresses removed.) At run time it also needs the curl program, which it starts as a child process for HTTP, and the system time-zone database. Writing a small JSON parser inside the project would shrink the binary a lot, and would also move the JSON parser out of the trusted base and into the verified code. It wasn't done because it's a lot of proof for a project this size.

Isn't it strange that the language is also the prover?

It's the main reason Lean was chosen. In many verification setups, the thing you verify is a model of the program: a TLA+ spec of a protocol, say, which you then re-implement in C++ and hope the two match. Here there's no gap of that kind. The select in the theorem is the select in the binary.

There is still one gap, and it's important to be clear about it. The kernel checks the definitions. The compiler translates those same definitions to C, separately, and the compiler isn't verified. If it miscompiled select, the proofs would still be right about the definition, and the binary would be wrong. That's row 2 of the trusted base in Lesson 12, covered by tests that run the real binary rather than by proof. (Lean also has ways to swap in a different run-time implementation for a definition, via attributes like @[implemented_by] and @[extern]. A search confirms this repository uses neither.)

Try it

After a build, open .lake/build/ir/LakeLevel/Impl/Decimal.c and find roundFrac. Match each line of the Lean source to the C. Then open .lake/build/ir/LakeLevel/Proofs/Decimal.c, the C for a file that contains only theorems, and see how little is in it.
