Lesson 1

What formal verification is (and isn't)

Formal verification means writing down exactly what "correct" means for a piece of code, and then having a program check a proof that the code meets that definition for every possible input.

Tests and proofs

Here's a unit test you might write for a function that rounds to two decimal places:

TEST(Round, HalfGoesUp) {
  EXPECT_EQ(round2("2.675"), "2.68");
  EXPECT_EQ(round2("-2.675"), "-2.68");
  EXPECT_EQ(round2("677.58"), "677.58");
}

It's a good test. But logically it says only "there exist three inputs on which the function is right". Whether it's right on the other inputs is up to you to guess.

A formal specification says what "right" means for every input. In this project, the rounding spec says, roughly:

For every exact decimal x, the answer k is within ½ of x; and if x is exactly halfway between two candidates, k is the one farther from zero.

A proof is an argument that the code always gives an answer of that kind. It's written in a language that a program can check mechanically, step by step, so you don't have to take anyone's word for it, including the author's.

C++ analogy

You already rely on a proof checker every day: the type checker. When your code compiles, the compiler has proved that no call anywhere passes a std::string where an int is expected. It proved this for every possible run, without running anything. static_assert is a tiny step further: a fact checked at compile time.

Formal verification extends that idea. The "types" become claims you choose, such as "this function returns the most recent reading" or "this program never exits 0 after failing to send an alert". If the proof checks, the claim holds.

The three pieces

Every verified component in this project has three parts, kept in three separate directories:

PieceWhat it isWhere
SpecWhat "correct" means. Statements and definitions, deliberately without an algorithm.LakeLevel/Spec/
ImplementationThe code that actually runs.LakeLevel/Impl/
ProofA machine-checked argument that the implementation meets the spec.LakeLevel/Proofs/

Here is the most important theorem in the project, the formal version of the product spec's sentence "it should never silently fail to alert":

/-- **R62: "it should never silently fail to alert."** If the run exits 0 and
the alert condition held, the alert was delivered. -/
theorem never_silently_fails (argv : List String) (w : World) (cfg : Cfg) (S : Site) (R : Reading)
    (h : parseArgs argv = .ok cfg) (hf : Fetched cfg w S R) (ha : ShouldAlert cfg R)
    (h0 : exitCode argv w = 0) :
    Delivered w (alertReq cfg S R) := by

You don't need to read Lean yet (Lesson 5 covers it). In English it says:

For every command line argv and every possible world w (any HTTP response, any clock, any time zone, any reply from the notification service): if the arguments parsed to a configuration cfg, and the world sent a valid reading R, and an alert should be sent for R, and the program exited with status 0, then the world reported the alert as delivered.

Equivalently: there's no situation at all where the lake is over your threshold, the alert didn't go through, and the program exits 0. A cron job that checks the exit status can't be fooled.

Who checks the proof?

Lean, the language used here, has a small core called the kernel. Every proof, however it was produced, is reduced to a sequence of very basic logical steps that the kernel checks. The kernel is the part you trust. You don't have to trust the person who wrote the proof, or the clever automation that helped them, or the AI agents that wrote some of the proofs in this repository (Lesson 13). If the kernel accepts a proof, the theorem holds, provided the kernel itself is correct and the three standard axioms that everything rests on are consistent.

The repository checks this explicitly: scripts/Audit.lean asks the kernel, for every theorem, which axioms its proof ultimately depends on. A proof with a hole in it depends on an axiom called sorryAx and is reported as unproved:

$ lake env lean scripts/Audit.lean
theorems proved from standard axioms only: 139 (obligations + helper lemmas)
obligations (scripts/obligations.txt) fully proved: 48/48
theorems still depending on sorry: 0
definitions still depending on sorry: 0

What "verified" does not mean

This is where people get misled, so it gets a whole section.

  1. The spec could say the wrong thing. The kernel checks that the proof proves the statement. It cannot check that the statement is what you meant. If the spec says "round towards zero" and you meant "round half up", you'll get a perfectly verified program that does the wrong thing. Reading the theorem statements carefully is a human job, and the most important review in the whole project. Lesson 6 is about this.
  2. The spec could be a copy of the code. If the spec computes the answer the same way the implementation does, the proof goes through and shows nothing, because a mistake in one is the same mistake in the other. Nothing in Lean, or in formal verification generally, detects this. Lesson 4 is about this.
  3. Proofs are about a model of the world. The theorem above is about what the world reports. If the code that talks to the network is wrong (say it reports every POST as HTTP 200), every theorem stays true and the tool can still fail to alert. That code is outside the proofs, and the project handles it differently (by keeping it tiny and testing it hard; Lesson 12).
  4. The compiler isn't verified. Lean's compiler turns the proved definitions into a native binary. A compiler bug could make the binary differ from what was proved. (Some research compilers, like CompCert for C, are themselves verified. Lean's isn't.)
In short

Whatever the proofs don't cover ends up in a small, named part of the system, and that's where the tests go.

What it costs

Lines of Lean in this project:

LayerLines
Spec (Types.lean + Spec/)411
Implementation (Impl/)450
Proofs (Proofs/)1,826
Unverified shell (Main.lean)80

The proofs are about four times the size of the code they verify. That ratio is typical, and it's why formal verification gets aimed at the parts where being wrong is expensive: crypto, consensus protocols, OS kernels, flight software. In this project, it's the part of the tool that decides whether to send an alert.

The flavors of formal verification

You'll hear these names. They're different tools for different jobs.

KindExamplesHow it works
Proof assistantsLean, Rocq (formerly Coq), IsabelleYou write the spec and the proof; the kernel checks it. The most expressive kind and the most work. This project.
Auto-active verifiersDafny, Why3, Frama-C (for C)You annotate code with pre/postconditions and loop invariants; an automatic solver (SMT) tries to do the proof for you.
Model checkersTLA+ (TLC), CBMC (for C/C++), SPINExplore every reachable state of a (usually bounded) model and report a counterexample trace if a property fails.

So where's the program?

If you browse the repository, you'll find no C++, Python, Rust or Java outside the test directory. That's because Lean is also an ordinary programming language: the functions the proofs are about are the same functions that get compiled into the lake-level binary. There's no separate model to fall out of sync with the code. Lesson 11 follows the code from .lean files to a native executable, and shows where the proofs go (they produce no machine code at all).

Try it

Before reading on, think of a function you've written recently. Try to state, in one sentence, what it means for it to be correct for every input, without describing how it works. If that's hard, you've found the hardest part of formal verification. It's also the part that finds the most bugs, as the next two lessons show.
