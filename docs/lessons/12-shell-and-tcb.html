The shell and the trusted base

Stage 6 lists everything the proofs assume, and adds tests aimed at those assumptions. Without this stage, "formally verified" would claim more than the proofs actually show.

Stage 6 commit 58b905b what changed since stage-5 Main.lean docs/06-shell-and-tcb.md

The shell

Main.lean is the only code that touches the outside world. Its core is an interpreter for Prog, one line per constructor:

/-- The interpreter: one line per `Prog` constructor. -/
partial def interp : Prog → IO UInt32
  | .done e => return e.toUInt32
  | .get r k => do interp (k (← httpGet r))
  | .zoneAt t k => do interp (k (← zoneAt t))
  | .clock k => do interp (k (← now))
  | .out s k => do IO.print s; (← IO.getStdout).flush; interp k
  | .err s k => do IO.eprint s; (← IO.getStderr).flush; interp k
  | .post r k => do interp (k (← httpPost r))

Read .get r k => do interp (k (← httpGet r)) as: "perform the GET for real, pass the answer to the continuation k, and interpret whatever program it returns". The shell makes no decisions. What to fetch, what to print, whether to alert and which exit status to return were all decided by the verified LakeLevel.main.

The rest of the file runs curl as a child process for HTTPS, rather than having the project implement HTTP and TLS itself. curl is very widely used, which makes it a reasonable thing to trust.

/-- Common curl flags: quiet but report errors, 30 s total (A21), HTTPS only,
and print the status code on a final line of its own. -/
def curlBase (req : Request) : Array String :=
  #["--silent", "--show-error", "--max-time", "30", "--proto", "=https",
    "--request", req.method, "--write-out", "\n%{http_code}"] ++
  (req.headers.toArray.flatMap fun (k, v) => #["--header", s!"{k}: {v}"])

/-- Split curl's output into body and the status line it appended. -/
def splitStatus (out : String) : Option (String × Nat) :=
  match out.splitOn "\n" |>.reverse with
  | code :: rest => code.toNat?.map fun n => ("\n".intercalate rest.reverse, n)
  | [] => none

Every flag here is an assumption about how curl behaves. --write-out "\n%{http_code}" assumes curl appends a newline and the status code after the body. --max-time 30 assumes curl gives up after 30 seconds. --proto =https assumes it refuses anything else. None of that can be proved in Lean. All of it is checked below.

The trusted computing base

The trusted computing base (TCB) is everything the guarantees depend on but don't check. Here it is in full, from docs/06:

#TrustedIf it's wrongMitigation
1Lean kernel and its three standard axiomsa false theorem is acceptedindustry-standard foundation; the audit confirms nothing else is used
2Lean compiler (Lean → C → native)the binary doesn't behave like the proved definitionsend-to-end and differential tests run the binary

9hydromet.lcra.orgsends wrong numbersout of scope: no software can verify its inputs are true
10ntfy.shsays 2xx, then doesn't deliverout of scope

Why row 6 matters most

Recall the headline theorem: in every world, if the alert condition held and the program exited 0, the world reported a 2xx for the POST. "The world" is whatever Main.lean says it is. If httpPost had a bug that returned .response 200 for every POST, every theorem would still be true, and the tool would silently fail to alert, which is the exact failure the whole project exists to prevent.

That mutation was planted (Lesson 10), and the end-to-end suite caught it: 7 checks failed, including HTTP 500 → exit 1.

Where the risk went

Before the proofs, the risk was spread across about 450 lines of logic. Afterwards, it's concentrated in 80 lines of shell plus a list of external components, each named, each with a test aimed at it. What formal verification gives you here is knowing exactly where the remaining risk is.

Tests aimed at the trusted base

1. A contract test against real curl

test/curl-contract.sh starts a small local HTTP server and runs the real curl with the shell's exact flags:

# Same flags as Main.lean's curlBase, minus --proto =https (the local server is plain http).
base=(--silent --show-error --max-time 30 --write-out $'\n%{http_code}')

body=$'Site lake level is 677.58 ft (MSL) as of 2026-10-20T03:55:09Z.\nLevel has reached the alert threshold.'
for code in 200 500; do
  out=$(printf '%s' "$body" | curl "${base[@]}" --request POST --header 'Title: t' \
        --data-binary @- --output /dev/null -- "http://127.0.0.1:$port/$code"; echo "|rc=$?")
  check "POST $code: stdout is exactly \\n$code, curl exits 0" $'\n'"$code|rc=0" "$out"
done
ok   POST 200: stdout is exactly \n200, curl exits 0
ok   POST 500: stdout is exactly \n500, curl exits 0
ok   POST body arrives byte-identical (newline preserved)
ok   GET: body, \n, status as the last line, curl exits 0
ok   --header User-Agent replaces curl's default
ok   refused connection: curl exits 7
ok   refused connection: message on stderr
ok   --proto =https refuses plain http (exit 1)

The second line is the important one. Curl exits 0 on an HTTP 500, because as far as curl is concerned the request worked and the server simply refused it. If the shell treated curl's exit status as "delivered", every failed alert would look successful. The contract test pins that behavior down.

2. A fake curl that can't drift

The end-to-end tests run the real binary, with a fake curl first on PATH. The fake logs every call and answers with whatever the test asks for:

if [ "$method" = POST ]; then
  cat > "$FAKE_LOG/$n-POST.body"
  [ -n "${FAKE_STDOUT:-}" ] && stat -c %s "$FAKE_STDOUT" > "$FAKE_LOG/$n-POST.stdout-bytes-before"
  if [ "${FAKE_FAIL:-}" = post ]; then echo "curl: (28) Operation timed out after 30001 milliseconds" >&2; exit 28; fi
  printf '\n%s' "${FAKE_POST_STATUS:-200}"
else
  if [ "${FAKE_FAIL:-}" = get ]; then echo "curl: (6) Could not resolve host: hydromet.lcra.org" >&2; exit 6; fi
  cat "$FAKE_GET_BODY"
  printf '\n%s' "${FAKE_GET_STATUS:-200}"
fi

A fake is only useful if it behaves like the real thing. This one reproduces exactly the output format the contract test verified against real curl: body, newline, status, exit 0. So if curl's behavior ever changed, the contract test would fail, rather than the fake silently drifting away from reality.

C++ analogy

It's the standard problem with mocks: a mock of HttpClient encodes your belief about HttpClient. A contract test runs the same assertions against the real dependency and the mock, so the belief is checked too.

3. End-to-end tests of the binary

test/e2e.sh has 65 checks. They cover the exact report text, the JSON (parsed by Python, not compared as text), the URL and headers sent, every usage error (exit 2 and zero curl calls), every bad-response fixture (exit 1, nothing on stdout, no POST), HTTP 500/302 and timeouts on the alert (exit 1), and a bogus TZ. One check is worth pointing out: R52, "report before alert", checked at run time.

eq "report fully written before POST (R52)" "$(stat -c %s "$out")" "$(cat "$log"/1-POST.stdout-bytes-before)"

When the fake curl receives the POST, it records how many bytes of the binary's stdout already exist. The test requires that to equal the final size. The theorem proves the Prog orders them correctly; this checks the shell actually flushed stdout before starting curl.

4. Side by side with the original

test/differential.sh runs the original Python and the new binary on the same fixtures. Every difference has to be one the ambiguity register decided on purpose; anything else would be a bug in one of them. A selection from the output, with the alert threshold set to 600:

What is still not covered

  • Real ntfy delivery was never exercised. POSTing to ntfy.sh publishes to a public topic, so it was left for the owner to run deliberately: lake-level --threshold 0 --ntfy-topic <your-topic>.
  • The 30-second timeout actually firing wasn't tested end to end. That the flag is passed is tested; that curl honors it is assumed (row 7).
  • TLS certificate validation is curl's default and isn't tested here.
  • Compiler correctness (row 2) is covered only by tests of the binary.
  • The exact report and alert text is a template, proved only in the weak sense of "the implementation is that template". Its correctness rests on review against the PRD and on byte-for-byte tests.
Process note

"Not covered" sections are easy to leave out, and leaving them out is how a verified system gets over-trusted. The rule followed here: if a test environment can't cover something, say so plainly rather than writing a test that looks like it does.

Try it

Run scripts/check-all.sh. It does every check in order of strength: build (with proofs and compile-time tests), audit, curl contract, end-to-end, the check of these lessons, and the differential run against the original. Then pick a row of the TCB table and design one more test aimed at it.
