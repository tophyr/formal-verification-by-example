Lesson 10

Planted bugs: checking the checkers

Every check in this project was itself checked: the tests, the proofs, the shell tests, the audit, and the script that checks these lessons. The method is to ask "could this pass while being wrong?", then plant a bug and see whether it does.

This is called mutation testing: make a small, plausible change to the thing being checked, and require that the check fails. A check that can't fail tells you nothing, but it still makes you feel safe. The project applied this at six levels.

Level 1: the tests

Covered in Lesson 7. Four planted bugs in the implementation (tie-breaking, rounding direction, midnight as 00, any status ≥ 200 counted as success), each caught by a compile-time test.

Level 2: the proofs

A proof that still goes through with a broken implementation isn't checking anything. So the same experiment was run against the proofs, with one rule: build only the proof library (lake build LakeLevel), not the tests, so the tests can't be the thing that catches it.

What planted bugs can't detect

This experiment shows that the proofs depend on the code. It doesn't show that the specs are independent of it. If a spec were a copy of the implementation, planting a bug in the implementation would break the proof against it in just the same way. A copied spec passes this check (Lesson 4).

The outputs below were re-run for this lesson, in a scratch copy of stage-6.

The one the tests missed

The ambiguity register (A10) says siteNumber is optional: if the response has one, it must match the requested site; if it doesn't, that's fine. Here's the code:

/-- If present, `siteNumber` must equal the requested site (A10). -/
def checkSite (site : Nat) (j : Json) : Except String Unit :=
  match j.getObjVal? "siteNumber" with
  | .ok (.num n) =>
    if Dec.le (Dec.ofJson n) ⟨site, 0⟩ && Dec.le ⟨site, 0⟩ (Dec.ofJson n) then .ok ()
    else .error s!"response is for a different site than {site}"
  | .ok _ => .error "response siteNumber is not a number"
  | .error _ => .ok ()

Now plant a bug. It's a cautious-sounding change: "reject the response if siteNumber is missing".

-  | .error _ => .ok ()
+  | .error _ => .error "response has no siteNumber"

At the time, the whole test suite passed with this bug in place. Every fixture happened to contain a siteNumber, because every fixture was derived from a real response, and real responses have one. The proof doesn't care what the fixtures contain:

✖ [23/27] Building LakeLevel.Proofs.DecodeLemmas (326ms)
error: LakeLevel/Proofs/DecodeLemmas.lean:93:12: unsolved goals

site : Nat

hj : j.getObjVal? "siteNumber" = Except.error e
⊢ False
Some required targets logged failures:

Read the stuck goal: "in the case where the response has no siteNumber (hj), prove False". The proof had reached the "siteNumber absent" case of the spec, where the spec says the check succeeds, and the code now says it fails. It can't reconcile them, and it tells you exactly which case is the problem. A fixture without siteNumber was then added, so the tests catch it too:

  -- A10: siteNumber is optional. (Added after a proof caught a mutant these tests missed:
  -- every fixture had a siteNumber, so "reject when absent" passed the whole suite.)
  check "no siteNumber is fine" ((← decodes "no-site-number") matches .ok _)
Why this matters

A proof covers inputs that nobody thought to test. Here, that was a response shaped slightly differently from every real response we'd seen, which is the kind of thing that turns up in production a year later.

When a proof breaks for a shallow reason

The tie-breaking mutation is instructive for a different reason. Change < to ≤ in select, so that the last of several tied readings wins:

-  | r :: rest => some (rest.foldl (fun best x => if best.t < x.t then x else best) r)
+  | r :: rest => some (rest.foldl (fun best x => if best.t ≤ x.t then x else best) r)

The first failure is shallow:

error: LakeLevel/Proofs/Select.lean:108:6: Type mismatch
  hsel x l
has type
  Latest (x :: l) (List.foldl step x l)
but is expected to have type
  Latest (x :: l) (List.foldl (fun best x => if best.t ≤ x.t then x else best) x l)

The proof file has a private copy of the fold's step function, called step, and the mutant no longer matches it. That's a real failure, but not an informative one: it only says "this code isn't the code the proof was written for". So make the experiment fair and mutate the proof's copy too. Now the proof fails where the theorem is actually false:

error: LakeLevel/Proofs/Select.lean:48:33: unsolved goals
x : Reading
l : List Reading
⋮
h : ¬r.t < x.t
⊢ r.t ≤ x.t → x = r

(Hypotheses not needed for the point are elided.) We're in the case where x is not later than the current best r, and the goal says: if x is at least as late as r (so, exactly as late), then x must be r. That's false for two different readings with the same timestamp. The stuck goal is the counterexample: a tie.

Can the broken program still ship?

The executable imports the proof library (Main.lean starts with import LakeLevel, and LakeLevel.lean imports every Proofs module). So with any of these mutations, lake build lake-level fails too. A bug that breaks a proof can't be built into the binary.

Two qualifications
  • A failed build doesn't delete the binary from the previous successful build; it just doesn't replace it. "Can't ship" means "can't produce", not "can't run an old copy".
  • Breaking a proof stops the build. Deleting a proof doesn't. If someone removes a theorem that has become inconvenient, everything still compiles. That's what Level 5 is for.

Level 3: the shell

The proofs can't see Main.lean, the 80 lines of unverified code that do real I/O (Lesson 12). So it was mutated too, and the end-to-end tests had to catch each one:

Mutation of Main.leanEnd-to-end checks that failed
report every POST as HTTP 2007 (including HTTP 500 → exit 1)
write stderr to stdout34
drop --max-time 304
never print the report5
drop --proto =https4

The first row is the important one. If the shell lied and reported every POST as delivered, every theorem would still be true (they're about what the world reports), and the tool would silently fail to alert. Only a test can catch that, so that exact mutation was tried.

Level 4: the test harness

The end-to-end test runs the real binary with a fake curl that logs each call into a file named like 0-GET.args or 1-POST.args. A helper counts calls of each kind. The first draft of that helper was:

calls() { find "$log" -name "*.$1" | wc -l; }

Called as calls POST.args, it searched for *.POST.args, which matches nothing, so it returned 0 every time. Every "no alert was sent" check in the suite passed, and would have kept passing even if the program sent alerts constantly. The fix is one character:

calls() { find "$log" -name "*-$1" | wc -l; }

What found it was adding a positive control: a check, using the same counter, in a case where the answer must be 1. With the broken glob it read 0, and failed. Both counting expressions that the "zero" checks use now have one:

# Positive control: proves calls() can count a POST, so the "no POST" checks below aren't vacuous.
eq "one GET, one POST" "1 1" "$(calls GET.args) $(calls POST.args)"
C++ analogy

The same failure in a C++ test suite looks like EXPECT_EQ(mock.calls("send"), 0) with a typo in the method name. It always passes. If a test asserts that something didn't happen, add a sibling test showing the same assertion notices when it does.

Level 5: the audit

Two problems with the audit were found by the same question.

  • It counted things that weren't ours. The first draft reported "87 proved" with nothing proved, by counting lemmas Lean generates automatically (Lesson 6). Fixed by counting only theorems in the Proofs modules.
  • It couldn't notice a missing theorem. It checked that every theorem it found was proved. Delete a hard theorem, and there's nothing left to find. So the 48 obligation names were frozen into scripts/obligations.txt, generated from the stage-3 tag, and the audit requires every one of them:
  -- The obligations are frozen in scripts/obligations.txt (generated from tag stage-3).
  -- Each must still exist, still be a theorem, and be fully proved: deleting or
  -- weakening-by-removal a hard theorem cannot turn the audit green.
  let names := (← IO.FS.lines "scripts/obligations.txt").filter (· ≠ "")

For the negative test, rename never_silently_fails, as if it had been deleted. The build still succeeds, but the audit fails:

$ lake build LakeLevel
Build completed successfully (27 jobs).
$ lake env lean scripts/Audit.lean
theorems proved from standard axioms only: 139 (obligations + helper lemmas)
obligations (scripts/obligations.txt) fully proved: 47/48
OBLIGATIONS MISSING: [LakeLevel.never_silently_fails]
theorems still depending on sorry: 0
definitions still depending on sorry: 0
scripts/Audit.lean:77:0: error: audit failed
Process note: a mistake made while writing this lesson

The first attempt at that negative test also deleted the name from obligations.txt. The audit then reported 47/47 and passed. That isn't a bug in the audit, but it shows that the frozen list only protects you if changes to the list are themselves reviewed. In practice, that means a diff to scripts/obligations.txt in a pull request should get the same scrutiny as a diff that deletes a test file.

Level 6: these lessons

The code excerpts on these pages are checked against the repository by scripts/check-lessons.py. Before trusting it, it was given two known-wrong excerpts (one with an extra trailing space, one with its line range shifted by one), and it reported both.

One check didn't get a negative control, so it's reported here as unknown rather than as passed. The Lean toolchain ships with an independent proof re-checker, leanchecker. Running lake env leanchecker LakeLevel exits 0 in about 8 seconds, and it does fail on a nonexistent module. But no forged proof was built to show that it rejects a bad one, so that run is evidence of unknown strength.

Doing it yourself

git worktree add ../mutant stage-6        # a scratch copy; your checkout stays clean
cd ../mutant
$EDITOR LakeLevel/Impl/Select.lean        # plant one bug
lake build LakeLevel                      # proofs only: does a proof break?
lake build Tests                          # do the tests catch it too?
cd - && git worktree remove --force ../mutant
Try it

Find a mutation of the implementation that no proof catches. There are some: for example, change the wording of an error message. Then explain why it's fine for no proof to catch it (which requirement, if any, it violates), or write the theorem that would.
