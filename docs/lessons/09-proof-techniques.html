Lesson 9 · Stage 5

How the hard proofs got done

The whole-program theorems were short because the hard parts had been pushed into lemmas. This lesson is about those lemmas: the handful of techniques that did most of the work, and the places where the tools themselves were surprising.

Stage 5 commit d570d87 LakeLevel/Proofs/ at stage-5 docs/05-proofs.md

1. Bridge lemmas: state it in ℚ, prove it in ℤ

The specs are about exact rationals, because that's what they mean. But Lean's best automation is omega, which decides linear arithmetic over integers, and it knows nothing about fractions. So one lemma clears the denominators:

theorem frac_lt (N M : Int) (D E : Nat) (hD : 0 < D) (hE : 0 < E) :
    (N : Rat) / (D : Rat) < (M : Rat) / (E : Rat) ↔ N * E < M * D := by

It's the schoolbook rule a/b < c/d ⇔ a·d < c·b for positive denominators. Its proof is about ten lines of fiddly rational arithmetic. Then every theorem after it (comparison, subtraction, rounding, and uniqueness of rounding) rewrites with it once and finishes with omega on integers.

C++ analogy

It's the same move as the implementation's: Dec.le compares by cross-multiplying instead of dividing. You choose a representation in which the hard operation disappears, then do the work there.

2. Splitting a proof into algebra and an exhaustive check

The calendar was the hardest part. Inverting Hinnant's formula means recovering the year within a 400-year era from the day within the era:

yoe = (doe − doe/1460 + doe/36524 − doe/146096) / 365

where every / is integer division. omega couldn't prove this in one go. The solution was to split it into a general fact that omega can prove, and a finite fact that can be checked case by case:

/-- Year-of-era from day-of-era, as in `ofDays0`. -/
def yoeOf (doe : Nat) : Nat := (doe - doe / 1460 + doe / 36524 - doe / 146096) / 365

/-- First day-of-era of era-year `yoe`. -/
def start (yoe : Nat) : Nat := yoe * 365 + yoe / 4 - yoe / 100

/-- Length of shifted (March-based) era-year `yoe`: it ends with the February
of Gregorian year `yoe + 1` (mod 400). -/
def len (yoe : Nat) : Nat := if leap (yoe + 1) then 366 else 365

theorem yoeOf_succ (a : Nat) : yoeOf a ≤ yoeOf (a + 1) := by
  unfold yoeOf; omega

theorem yoeOf_mono {a b : Nat} (hab : a ≤ b) : yoeOf a ≤ yoeOf b := by
  induction b with
  | zero => have : a = 0 := by omega
            subst this; exact Nat.le_refl _
  | succ n ih =>
    rcases Nat.lt_or_eq_of_le hab with h1 | h1
    · exact Nat.le_trans (ih (by omega)) (yoeOf_succ n)
    · subst h1; exact Nat.le_refl _

/-- The finite part, checked by the kernel for all 400 era-years. -/
theorem endpoints : ∀ y, y < 400 →
    yoeOf (start y) = y ∧ yoeOf (start y + len y - 1) = y ∧
    (y < 399 → start y + len y = start (y + 1)) ∧ (y = 399 → start y + len y = 146097) := by
  decide +kernel

theorem yoeOf_eq {yoe doy : Nat} (hy : yoe < 400) (hd : doy < len yoe) :
    yoeOf (start yoe + doy) = yoe := by
  have ⟨e1, e2, _, _⟩ := endpoints yoe hy
  have := yoeOf_mono (a := start yoe) (b := start yoe + doy) (by omega)
  have := yoeOf_mono (a := start yoe + doy) (b := start yoe + len yoe - 1) (by omega)
  omega

The argument:

  1. Monotone (yoeOf_succ, yoeOf_mono): the formula never goes down as the day increases. omega proves the one-step version directly; induction extends it.
  2. Right at both ends of every year (endpoints): for each of the 400 years in an era, the formula gives the right year on its first day and its last day. decide +kernel checks all 400 cases by evaluation inside the kernel.
  3. So right in between (yoeOf_eq): a function that never decreases and gives y at both ends of an interval gives y everywhere in it.

That covers all 146,097 days of an era without checking them one by one. The finite check counts as a real proof because the kernel does the evaluating.

Why native_decide was forbidden

Lean has a faster alternative, native_decide, that compiles the check to native code and runs it. It's much quicker, but it means trusting the compiler (and adds an extra axiom, Lean.ofReduceBool, to the proof). Since the whole point is to trust only the kernel, it was banned, and the audit flags any theorem that depends on that axiom.

3. Shape lemmas: name the few shapes a run can have

Reasoning about every possible run of the program sounds hard, but this program's runs have very few shapes. run_ok_cases proves there are exactly two for a valid command line:

/-- **Every run with a valid configuration has one of two shapes**: (a) nothing
valid was fetched, and the run is the GET then one error line, exit 1; or
(b) the GET, the zone/clock queries, the report, then whatever `finish` does. -/
theorem run_ok_cases (argv : List String) (w : World) (cfg : Cfg) (h : parseArgs argv = .ok cfg) :
    ((¬ ∃ S R, Fetched cfg w S R) ∧
      ∃ m, (main argv).run w = ([.get (fetchReq cfg), .err (errLine (sanitize m))], 1)) ∨
    (∃ S R, Fetched cfg w S R ∧
      (main argv).run w =
        (.get (fetchReq cfg) :: preReport cfg R ++ .out (reportFor cfg w S R) ::
            ((finish cfg S R).run w).1,
         ((finish cfg S R).run w).2)) := by

It's proved once, by unfolding main and splitting on every branch. After that, most of the whole-program theorems are a few lines of case analysis on it, as you saw in Lesson 8. The same trick is applied one level down, with lemmas such as finish_events, "the alert step only ever POSTs the alert or writes to stderr".

4. Theorems about the spec itself

Some theorems aren't about the code at all:

/-- The rounding spec is *deterministic*: at most one correct answer.
(A spec with two acceptable answers would let two "verified" programs disagree.) -/
theorem RoundsTo.unique {x : Rat} {k k' : Int} (h : RoundsTo x k) (h' : RoundsTo x k') :
    k = k' := RoundsTo.unique' h h'

If RoundsTo allowed two answers for some x, two different programs could both be "verified" and still print different numbers. RoundsTo.unique and Latest.unique rule that out. They're the formal version of testing your tests: checking that the spec is as tight as you think it is.

5. Refactoring so the code can be proved

At stage-4, decode was one do block:

/-- Validate a decoded JSON response for `site`, and pick its most recent reading. -/
def decode (site : Nat) (j : Json) : Except String (Site × Reading) := do
  match j.getObjVal? "value1Type" with
  | .ok (.str "Head") => pure ()
  | _ => throw "response is not lake-level (Head) data"
  match j.getObjVal? "siteNumber" with
  | .ok (.num n) =>
    unless Dec.le (Dec.ofJson n) ⟨site, 0⟩ && Dec.le ⟨site, 0⟩ (Dec.ofJson n) do
      throw s!"response is for a different site than {site}"
  | .ok _ => throw "response siteNumber is not a number"
  | .error _ => pure ()
  let recs ← match j.getObjVal? "records" with
    | .ok (.arr a) => pure a
    | _ => throw "response has no records array"
  let rs ← recs.toList.mapM parseRecord
  match select rs with
  | some r => pure (SiteOf site j, r)
  | none => throw "API returned no records"

Its control flow was hard to take apart in a proof: every match and throw desugars into nested binds. It was split into named steps, each with its own small lemma ("checkSite succeeds if and only if …"):

/-- Validate a decoded JSON response for `site`, and pick its most recent reading. -/
def decode (site : Nat) (j : Json) : Except String (Site × Reading) := do
  checkHead j
  checkSite site j
  let recs ← getRecords j
  let rs ← recs.toList.mapM parseRecord
  let r ← pickLatest rs
  pure (SiteOf site j, r)

Behavior, check order and error messages are unchanged, and the tests still pass. In this case, the version that was easier to prove was also easier to read. The full change is in the stage-5 diff.

6. When the proof finds the spec was too weak

At stage-4, three rendering theorems carried an extra hypothesis:

/-- Rendered text has the promised shape … -/
theorem fixed_shape (n : Nat) (k : Int) (hn : 1 ≤ n) : FixedShape n (fixed n k) := sorry

"For at least one decimal place". When the proofs were written, Lean's linter reported that hn was never used. That means the theorem holds without it. Removing it made the theorem stronger: it now also covers n = 0, integer rendering, which the "N min ago" text actually uses and which was therefore unverified before.

/-- Rendered text has the promised shape … -/
theorem fixed_shape (n : Nat) (k : Int) : FixedShape n (fixed n k) := fixed_shape' n k

That's the right direction for a statement to change after it's frozen. Dropping a hypothesis can only make a theorem cover more. Adding one would weaken it and deserves suspicion.

7. When the tools are surprising

Timestamps are declared as abbrev Instant := Int. An abbrev is a type alias, like using Instant = int64_t;. But omega doesn't look through it:

example (a b : Instant) (h : a < b) : a + 1 ≤ b := by omega

error: omega could not prove the goal:
No usable constraints found. You may need to unfold definitions so `omega` can see linear arithmetic facts about `Nat` and `Int`, which may also involve multiplication, division, and modular remainder by constants.

"No usable constraints found", while the constraint is sitting right there. The fix is to restate things at type Int, which is why the calendar and select proofs are sprinkled with lines like these:

/-- `civilOf` always produces a real civil time … -/
theorem civilOf_valid (t : Instant) (ht : minInstant ≤ t) : (civilOf t).Valid := by
  rw [minInstant_eq] at ht
  have ht : (_ : Int) ≤ _ := ht
  rw [civilOf_eq]
  dsimp only [Civil.Valid]
  have hn : 306 ≤ (t + 86400 * 719468).toNat / 86400 := by omega
  exact ⟨(Cal.ofDays0_valid_inv _ hn).1, by omega, by omega, by omega⟩

have ht : (_ : Int) ≤ _ := ht says "the same fact, but please see it as an Int comparison". Two independent proof efforts on this project ran into this.

Why this is only an annoyance

A tool that ignores your hypotheses can only make a true theorem look unprovable. It can never make a false one pass, because the kernel still checks whatever proof eventually gets produced. That's why proof assistants can use clever, unverified automation: the automation only proposes proofs, and the kernel checks each one.

Try it

Delete the line have ht : (_ : Int) ≤ _ := ht from civilOf_valid and run lake build. omega now reports "a possible counterexample may satisfy the constraints a ≤ -62162035200 where a := t": a moment long before year 1. It proposes that because it can no longer see ht, the hypothesis ruling it out. Then put the line back. Learning to read "why can't you prove this?" messages is most of the day-to-day skill of using a proof assistant.
