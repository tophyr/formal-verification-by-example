Lesson 2 · Stage 0

The program and its PRD

This lesson introduces the program the project rebuilds, and the product requirements document (PRD) that the work starts from. The program is small enough to understand completely, and real enough to have real bugs.

Stage 0 commit 1293568 browse the repo at stage-0 docs/00-prd.md

The program

The Lower Colorado River Authority runs the dams on the Highland Lakes in Central Texas. Their "Hydromet" site publishes readings from each dam through a public JSON API. For Mansfield Dam (site 3963), which holds back Lake Travis, a reading arrives every five minutes or so.

The starting point was an existing Python script of about 100 lines, lake_level.py. It fetches the JSON, picks the newest reading, prints it, and if you pass --threshold, POSTs a push notification to your phone through ntfy.sh when the lake is at or above that level. (The script is in this repository, unchanged, as test/original/lake_level.py. The tests in Lesson 12 run it side by side with the new version.)

Its output, and the output of the verified version, looks like this:

$ lake-level
Mansfield Dam (Lake Travis)
  Most recent lake level: 677.58 ft (MSL)
  Observed: 2026-10-19 10:55 PM CDT (5 min ago)
  Full pool: 681.0 ft  (+3.42 ft from full)

And for automation:

# crontab: alert me when Lake Travis reaches 685 ft
*/15 * * * *  lake-level --threshold 685 --ntfy-topic my-lake || echo "lake-level failed" | mail -s alert me

Why this program? It's small, but it has most of the things that make real software hard to get right: untrusted input from the network, decimal numbers, dates and time zones, command-line parsing, a side effect that must happen reliably (the alert), and exit codes another program depends on.

The PRD

Stage 0 is a product requirements document written the way you'd write one for a colleague: docs/00-prd.md. It has background, goals and non-goals, the API's URL and an example response, the output formats with examples, the command-line options, error handling, and acceptance criteria. Go and read it now; it's about three pages.

It's a good PRD. A competent developer could build the program from it, and the Python original is more or less what you'd expect them to produce. One sentence in §6 matters more than the rest:

Must be reliable enough to trust for flood alerting: it should never report a wrong level, and should never silently fail to alert.

The later stages are all aimed at making that sentence true, and at being able to show that it is.

Why prose isn't enough

Prose works well between people who share context. "Print the most recent reading" is clear to the author, who knows what the data looks like. But most sentences leave some cases unstated, and different readers fill them in differently. A developer usually fills them in with whatever their language does by default, and that's where most of the bugs in Lesson 3 come from.

Try it before you read Lesson 3

Read the PRD and write down every question it doesn't answer. Aim for at least eight. For each, ask: "if two developers answered this differently, could one of their programs give a wrong answer, or fail to alert?"

Some of the questions Stage 1 found
  • "Most recent" by what? The timestamp text, or the moment it denotes? What if two readings tie?
  • "Two decimal places": rounded how? What's 2.675?
  • What counts as a valid --threshold? Is nan a number?
  • "At or above the threshold": compared with the exact level, or the rounded one on screen?
  • What happens if one record in the response is malformed?
  • An unknown site returns HTTP 200 with an empty list. Is that "no readings"?
  • Is the data even a lake level? (The response has a field that says what kind of value it is.)
  • What may a user put in --site, given it's pasted into a URL?
  • What does "the notification fails to send" mean, exactly? Which HTTP statuses count as success?
  • Which time zone is "local"? At what moment (daylight saving changes the offset)?

Stage 1 ended up with 21 of these, and three turned out to be real bugs in the original.

Process note

The PRD was written from the original program's behavior and its obvious intent, not as a precise description of what the Python does. That matters later: Stage 1 treats the Python as "what a competent developer produced from prose like this", and checks it against the requirements. If the PRD had been reverse-engineered from the code, it would have encoded the code's bugs as requirements.
