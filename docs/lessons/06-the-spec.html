Lesson 6 · Stage 3

The spec, in Lean, with nothing proved

Stage 3 writes the model down in Lean so that a machine accepts it. There's no implementation yet, and no proofs: every function body and every proof is sorry. What this stage produces is the list of theorem statements, which together define precisely what "done" means.

The import rule stops one shortcut: the spec can't be defined in terms of the implementation. Without it, someone could write RoundsTo x k := k = roundFrac x.num x.den, and the proof would be one line that shows nothing. The rule doesn't stop the same algorithm from being typed out a second time inside the spec. That's the problem from Lesson 4, and only review catches it. Where a spec needs something the implementation provides (the timestamp spec needs "the instant of a civil time"), it takes it as a parameter (secs : Civil → Instant) instead of importing it.

At this stage the implementation is just signatures:

def select (rs : List Reading) : Option Reading := sorry

Four specs worth reading closely

Rounding, by relation

/-- **Rounding, relationally** (A4). `k` is a correct rounding of `x`, ties
away from zero:

* `x` is strictly within ½ of `k`, or
* `x` is exactly ½ below `k` and positive (so `k` is farther from zero), or
* `x` is exactly ½ above `k` and negative (likewise).

No algorithm is given. Stage 5 proves exactly one `k` satisfies this. -/
def RoundsTo (x : Rat) (k : Int) : Prop :=
  ((k : Rat) - 1/2 < x ∧ x < (k : Rat) + 1/2) ∨
  (x = (k : Rat) - 1/2 ∧ 0 < x) ∨
  (x = (k : Rat) + 1/2 ∧ x < 0)

It's a yes/no question about a pair (x, k), over exact rationals. You could check an answer with it, but you can't compute one from it. The implementation (Lesson 7) will use integer division.

The calendar, by characterization

/-- "Tomorrow": the obvious successor of a date. -/
def nextDate (y mo d : Nat) : Nat × Nat × Nat :=
  if d < dim y mo then (y, mo, d + 1)
  else if mo < 12 then (y, mo + 1, 1)
  else (y + 1, 1, 1)

/-- **The day count, by characterization** (R23): `f` numbers days so that
1970-01-01 is day 0 and every valid date's successor is one more.
Any two such functions agree on every valid date. -/
def DayCount (f : Nat → Nat → Nat → Int) : Prop :=
  f 1970 1 1 = 0 ∧
  ∀ y mo d, ValidDate y mo d →
    let (y', mo', d') := nextDate y mo d
    f y' mo' d' = f y mo d + 1

DayCount is a property of a function f. It doesn't say how to compute a day number; it says what any correct day-numbering must satisfy. The obligation will be DayCount days: the implementation's days has the property.

A gap

The doc comment says "any two such functions agree on every valid date". That's true (it follows by induction along nextDate), but it isn't itself proved in this repository. It's the argument for why DayCount is a good spec, and you're trusting it on paper. Proving it would be a good exercise.

Timestamp parsing, as an inverse

/-- **What the timestamp parser must do**, in one equation (A2, R14, R41):
it accepts exactly the canonical renderings of acceptable civil times, and
returns the instant `secs` assigns them. -/
def ParsesTimestamps (parse : String → Option Instant) (secs : Civil → Instant) : Prop :=
  ∀ s t, parse s = some t ↔ ∃ c, c.Acceptable ∧ s = iso c ∧ t = secs c

One line says everything about the parser: for every string, it succeeds exactly when the string is the canonical rendering (iso) of a real date in range, and then it returns that date's instant. That one line covers strictness, range checking and meaning. iso is easy to get right because rendering is easy; parsing is the hard direction, and it's specified in terms of the easy one.

"The most recent reading", declaratively

/-- **"The most recent reading"**, declaratively, over list indices (A1, R20–R22):
`r` is at some index `i`; no reading is later than `r`; and every reading
*before* index `i` is strictly earlier (so `r` is the first of the latest). -/
def Latest (rs : List Reading) (r : Reading) : Prop :=
  ∃ (i : Nat) (hi : i < rs.length),
    rs[i] = r ∧
    (∀ (j : Nat) (hj : j < rs.length), rs[j].t ≤ r.t) ∧
    (∀ (j : Nat) (hj : j < i), (rs[j]'(Nat.lt_trans hj hi)).t < r.t)

Look at the last line. In Lean you can't write rs[j] unless you can prove j is a valid index. Here we only know j < i and i < rs.length, so the spec has to supply the proof explicitly: Nat.lt_trans hj hi, "j < i and i < length, so j < length". The maths notation of Stage 2 didn't need this, so nobody noticed it was missing. Lean wouldn't accept the spec without it.

C++ analogy

It's as if operator[] only compiled when the compiler could see a proof that the index was in bounds. There's no undefined behavior, and occasionally you have to explain to the compiler why your index is fine.

The obligations

The theorems to prove were all written at this stage, with sorry as the proof. Here's the headline one, as it was committed in Stage 3:

/-- **R62: "it should never silently fail to alert."** If the run exits 0 and
the alert condition held, the alert was delivered. -/
theorem never_silently_fails (argv : List String) (w : World) (cfg : Cfg) (S : Site) (R : Reading)
    (h : parseArgs argv = .ok cfg) (hf : Fetched cfg w S R) (ha : ShouldAlert cfg R)
    (h0 : exitCode argv w = 0) :
    Delivered w (alertReq cfg S R) := sorry

There are 48 such obligations. Their names are frozen in scripts/obligations.txt, generated from this tag, so that later stages can't quietly drop one.

Process note: the audit that said "87 proved"

The first draft of the audit counted every theorem in the LakeLevel namespace. It reported 87 proved before any proof had been written. Lean automatically generates small lemmas for every structure (for example, "two Decs are equal if and only if their fields are"), and those really are proved. They just aren't ours. A count that looks like progress but isn't would have misled every later stage, so the audit was fixed to count only theorems in LakeLevel.Proofs.* modules before this commit. The fix is the inModule and autoGen filters in the audit script.

What type-checking alone bought

Nothing is proved yet, but having Lean accept the spec already rules out a class of mistakes prose can't avoid. Every term is defined. Every "for all" ranges over a definite type. Every function gets the right number and kind of arguments. And writing it forced decisions the maths version glossed over: Latest's index proof above, and ValidResp having to say exactly how the list of JSON records corresponds to the list of readings (equal lengths, index by index).

Did we state the right thing?

This is the question the kernel can't answer. A green audit later will mean "each statement follows from the definitions". It won't mean "the statements say what the PRD meant". The only way to close that gap is for people to read the statements in Proofs/ against the requirements, which is why they're kept short and named after requirement numbers.

So read them critically. Here's one where the statement is weaker than the requirement:

/-- Repeating an option is a usage error (A20), for every pair of values. -/
theorem parseArgs_dup (o v w : String)
    (ho : o ∈ ["--site", "--type", "--threshold", "--ntfy-topic"]) :
    ∃ m, parseArgs [o, v, o, w] = .usage m := by

A20 says any option given twice is an error. This proves it only for the argument list [o, v, o, w]: the option, a value, the same option, another value, and nothing else. It says nothing about --site 1 --json --site 2, or --site=1 --site 2. (The implementation does reject those, and the end-to-end tests try --json --json, but that's tested, not proved.) Similarly, parseArgs_site and its siblings are about a command line containing only that one option.

Found while writing this lesson

This weakness wasn't flagged in the stage documents. It was noticed while writing this page, by reading the statements against the requirements, which is exactly the review the paragraph above says is needed. The general theorem is provable; it's a good exercise (below).

Some obligations are deliberately weak, and say so: fetchReq_eq and signed_eq are "template equations", proved by rfl ("both sides are literally the same once definitions are unfolded"). They're there so the template is written down in a theorem a reviewer will read, not because they prove anything deep.

Try it

Write the statement (just the statement, ending in := sorry) of a stronger duplicate-option theorem: "for every argument list in which some valued option occurs twice (in either --opt v or --opt=v form), parseArgs returns .usage". You'll find that saying "occurs twice" precisely is most of the work.
