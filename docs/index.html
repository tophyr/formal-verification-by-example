Formal Verification by Example

What does it actually take to prove a program correct? These lessons answer that with one small, real tool: it fetches the Lake Travis water level and sends an alert when it's high. We start from a one-page spec and end with a compiled binary and 48 proofs that Lean has checked. Each step is a commit you can check out. You'll need C++-level programming experience and no theory.

The repository is the course material. Every stage of the work is one git commit with a tag (stage-0 to stage-6), so you can check out any stage and see the project exactly as it stood. The lessons link to those commits and to the exact lines of code they discuss.

What formal verification is, and why you'd want it

Formal verification is a way of proving that a program is correct for every possible input, not just the ones you test. You write down exactly what "correct" means, as a precise statement such as "if the lake is above the threshold and the program exits 0, the alert was delivered". Then you write a proof that your code meets it, and a tool checks the proof. If the check passes, no input exists that breaks the statement, however unlikely.

Part of the payoff comes before any proof. Writing down exactly what "correct" means forces questions that ordinary specs skip. Doing that turned up a real bug in the original hundred lines of Python that was the inspiration for this project: it accepts --threshold nan and then never sends an alert, because every comparison with NaN is false. The rest of the payoff is the bugs that tests miss. Of the bugs planted in this project to check the proofs, one got past every test and was caught only by a proof.

It isn't free. Here, the proofs are about four times the size of the code they cover. And a proof only guarantees what its statement says, so a carelessly worded statement proves the wrong thing. It's worth it where a mistake is expensive and the inputs are too varied to test exhaustively: parsers, protocols, money, or anything that decides whether to wake someone up.

One of the common tools used for this type of work is a programming language called Lean, which can check proofs about its code. Lesson 1 shows what that looks like, and Lesson 5 teaches enough of it to read every file in the repository.

What you need

  • Background: you can read C++ or a similar language, and you've written unit tests. No maths beyond high school. Symbols like ∀ and → are explained when they first appear, and Lesson 5 has a cheat sheet.
  • Time: about three to four hours to read everything; longer if you do the "Try it" exercises.
  • To run things yourself (optional): git, curl, python3, and elan (Lean's version manager, similar to rustup). The repository pins Lean 4 v4.35.0 and uses nothing outside Lean's core library.

The stages

The project is built in seven stages. Each one takes something vague from the stage before and makes it more exact, and each catches a different kind of mistake.

Running it yourself

git log --oneline --decorate     # the seven stages
git checkout stage-3             # e.g. the spec, nothing proved yet
git checkout main

lake build                       # type-check spec + impl + proofs, run tests, link binary
lake env lean scripts/Audit.lean # ask Lean's kernel what every theorem depends on
scripts/check-all.sh             # every check, in order of strength
.lake/build/bin/lake-level --help

The repository's README and its per-stage documents in docs/*.md are the reference material for the same work.
