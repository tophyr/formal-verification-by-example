Lesson 6

Reading Lean, part 2: statements and theorems

The second of three lessons on reading Lean. It covers statements, which a program can't always compute but Lean can prove, and theorems, which prove them. The spec in Lesson 7 is written in both.

This lesson builds on the functions and data types of Lesson 5. As there, every example is real code from the repository at stage-6.

Statements: Prop versus Bool

This is the first real difference from C++. A Bool is a runtime value, true or false. A Prop is a statement, which might be true or false and which you might be able to prove. 2 + 2 = 4 is a Prop. So is "every list has a latest reading", which you can't compute but can prove.

/-- HTTP success. -/
def ok2xx (status : Nat) : Prop := 200 ≤ status ∧ status < 300

instance (s : Nat) : Decidable (ok2xx s) := by unfold ok2xx; infer_instance

/-- The world delivered this POST. -/
def Delivered (w : World) (q : Request) : Prop :=
  ∃ status, w.post q = .response status ∧ ok2xx status

ok2xx is a statement about a status code (∧ is "and"; the table at the end of this lesson lists the other symbols). A Prop can't go in an if by itself, because Lean has no general way to compute whether a statement is true. The instance … Decidable line supplies a way for ok2xx, so the program may use if ok2xx st then …; without it, that if fails to compile. An instance is roughly like specializing std::hash for your own type: it tells the compiler how to provide something, here Decidable (ok2xx s) for any s, and the compiler finds it whenever it's needed.

The part after by builds that instance using tactics, which Lesson 9 covers. Briefly: unfold ok2xx replaces ok2xx s with its definition, 200 ≤ s ∧ s < 300, and infer_instance asks Lean to build the instance from ones it already has: comparisons of Nats are decidable, and so is an "and" of two decidable statements. The unfold is needed because Lean's search for instances doesn't look inside a def.

Delivered says "there exists a status such that the world answered the POST with that status, and it's 2xx". It's never computed; it only appears in theorems.

A spec and its implementation

Specs are written as Props so they can say things code can't, like "for every list" or "there exists an index". The implementation is written with Bools so it can run. Compare the spec of a decimal's value with the implementation of comparison:

/-- The rational number a `Dec` denotes: `m / 10^e`. All semantics go through this. -/
def Dec.val (d : Dec) : Rat := (d.m : Rat) / ((10 ^ d.e : Nat) : Rat)
/-- Exact comparison `a ≤ b`, by cross-multiplying: `a.m·10^b.e ≤ b.m·10^a.e`. -/
def Dec.le (a b : Dec) : Bool :=
  decide (a.m * ((10 ^ b.e : Nat) : Int) ≤ b.m * ((10 ^ a.e : Nat) : Int))
  • Dec.val and Dec.le are the functions val and le in the namespace Dec. With a dot call, d.val is Dec.val d, and a.le b is Dec.le a b.
  • (x : T) means "x, as a T", and converts when needed, like static_cast<T>(x). Dec.val converts d.m to a Rat and divides it by 10 ^ d.e, also converted, so the result is an exact fraction. In Dec.le, ((10 ^ b.e : Nat) : Int) computes 10 ^ b.e as a Nat and then converts it to an Int, so it can be multiplied by a.m.
  • Dec.le returns a Bool, but the comparison in its body is a Prop. decide turns that Prop into true or false by running its Decidable instance, the kind of instance described above for ok2xx.

Theorems are functions

Here's the theorem connecting those two:

/-- Comparison is exactly rational `≤`. -/
theorem Dec.le_iff (a b : Dec) : Dec.le a b = true ↔ a.val ≤ b.val := Dec.le_iff' a b

Read it as a function declaration, because that's literally what it is:

  • the name is Dec.le_iff;
  • the parameters are (a b : Dec). Any two decimals: the parameters are where "for all" comes from;
  • the return type is the statement: Dec.le a b = true ↔ a.val ≤ b.val, "the code says ≤ if and only if the true rational values are ≤";
  • the body, after :=, is the proof. Here it's just a call to a helper theorem Dec.le_iff' that does the real work.

A proof of "A implies B" is a function that takes a proof of A and returns a proof of B. A hypothesis is just a parameter whose type is a statement. In the headline theorem from Lesson 1, (h0 : exitCode argv w = 0) is a parameter: you can only call the theorem if you can hand it evidence that the exit code was 0.

So "the theorem is proved" means "this function type-checks". The type checker (the kernel) is the proof checker. (This correspondence between propositions and types, and proofs and programs, is called the Curry–Howard correspondence. You don't need the theory; you just need to know why a proof checker can look like a compiler.)

sorry: the placeholder

sorry closes any goal without proving it. The compiler accepts it with a warning. It's how you write a theorem's statement before its proof, the way you might write throw std::logic_error("TODO"). Anything built on sorry is marked as depending on the axiom sorryAx, which is how the audit finds it. In Stage 3, the subject of the next lesson, every proof in the repository was sorry.
