Code written with proofs in mind

The implementation is ordinary functional code, but each choice was made knowing it would have to be proved later. Most of those choices come down to using only operations that Lean's automation is good at.

Rounding with integers only

/-- Round `N / D` to an integer, ties away from zero: for `N ≥ 0`,
`⌊(N + D/2) / D⌋ = ⌊(2N + D) / 2D⌋`; mirrored for `N < 0`. -/
def roundFrac (N : Int) (D : Nat) : Int :=
  if 0 ≤ N then (2 * N + D) / (2 * D)
  else -((2 * (-N) + D) / (2 * D))

No floating point anywhere. Compare it with the spec RoundsTo from Lesson 6. The two have completely different shapes, as intended, and the proof connecting them is real work.

The calendar: a closed-form formula

/-- Days since 0000-03-01 (valid for year ≥ 1). -/
def daysFrom0 (y mo d : Nat) : Nat :=
  let y' := if mo ≤ 2 then y - 1 else y
  let era := y' / 400
  let yoe := y' % 400                                   -- year of era, [0, 399]
  let mp := if mo > 2 then mo - 3 else mo + 9           -- March = 0, [0, 11]
  let doy := (153 * mp + 2) / 5 + d - 1                 -- day of year, [0, 365]
  let doe := yoe * 365 + yoe / 4 - yoe / 100 + doy      -- day of era, [0, 146096]
  era * 146097 + doe

This is Howard Hinnant's well-known days_from_civil (Hinnant also wrote the date library that C++20's <chrono> calendar types were standardized from). It counts from 1 March of year 0, so the leap day falls at the end of each shifted year. It was chosen because every division is by a constant, and omega, Lean's linear-arithmetic solver, can reason about division by constants. A loop over months would have been easier to read and much harder to prove.

Executable specs

/-- Strict `YYYY-MM-DDTHH:MM:SSZ` parser. -/
def parseTs (s : String) : Option Instant :=
  match s.toList with
  | [y1, y2, y3, y4, '-', m1, m2, '-', d1, d2, 'T', h1, h2, ':', i1, i2, ':', s1, s2, 'Z'] => do
    let c : Civil :=
      ⟨← num4 y1 y2 y3 y4, ← num2 m1 m2, ← num2 d1 d2, ← num2 h1 h2, ← num2 i1 i2, ← num2 s1 s2⟩
    if c.Acceptable then some (secs c) else none
  | _ => none

The pattern is exactly 20 characters with the separators fixed; anything else is none. Then it calls c.Acceptable, the spec's own definition of a valid date, directly, because it's decidable and cheap. Running the spec as code is legitimate where the spec is already a simple check. It doesn't make the proof trivial: the proof still has to show that this 20-character match reconstructs exactly the date whose canonical text is the input.

The whole program, as a value

Here's main. Remember from Lesson 4 that it does no I/O. It returns a Prog: a tree of requests and continuations.

/-- After the report is written: alert if required (R50–R54). -/
def finish (cfg : Cfg) (S : Site) (R : Reading) : Prog :=
  match cfg.threshold with
  | some th =>
    if Dec.le th.value R.level then
      .post (alertReq cfg S R) fun
        | .response st =>
          if ok2xx st then .err (alertNotice cfg) (.done 0)
          else .err (errLine (sanitize s!"ntfy alert failed: HTTP {st}")) (.done 1)
        | .failed m => .err (errLine (sanitize s!"ntfy alert failed: {m}")) (.done 1)
    else .done 0
  | none => .done 0

def main (argv : List String) : Prog :=
  match parseArgs argv with
  | .help => .out helpText (.done 0)
  | .usage m => .err (errLine (sanitize m) ++ usageText) (.done 2)
  | .ok cfg =>
    .get (fetchReq cfg) fun
      | .failed m => .err (errLine (sanitize m)) (.done 1)
      | .response st body =>
        if ok2xx st then
          match decodeBody (siteNum cfg.site) body with
          | .error m => .err (errLine (sanitize m)) (.done 1)
          | .ok (S, R) =>
            if cfg.json then .out (jsonText S R) (finish cfg S R)
            else
              .zoneAt R.t fun z => .clock fun now =>
                .out (humanReport S R z now) (finish cfg S R)
        else .err (errLine (sanitize s!"hydromet returned HTTP {st}")) (.done 1)

Read .get (fetchReq cfg) fun | … => … as "GET this request; when the answer comes back, here's what to do for each kind of answer". Every exit status in the program is visible in these 30 lines. That was deliberate, and it's what makes the whole-program theorems in the next lesson provable.

A shorthand: | lines with no match

fun | .failed m => … | .response st body => … is short for a lambda whose whole body is a match on its argument: fun r => match r with | .failed m => … | .response st body => …. It's used when the argument only gets taken apart, so it doesn't need a name.

def has the same shorthand. A function's type written with an arrow, followed directly by | lines, with no parameter names and no :=, means a function whose body is a match on its argument:

def Meridiem.text : Meridiem → String
  | .am => "AM"
  | .pm => "PM"

is the same as def Meridiem.text (m : Meridiem) : String := match m with | .am => "AM" | .pm => "PM". You'll see it again in the shell's interpreter in Lesson 12.

Tests that run at compile time

test/Tests.lean is compiled as part of lake build. #guard e fails the build unless e evaluates to true, like a static_assert that can call any function. #eval blocks run arbitrary checks, including reading fixture files.

The rule for expected values: they never come from the implementation. They come from the PRD's examples, from the decisions in the ambiguity register, and from independent tools. Every epoch value here came from GNU date:

/-! ## Calendar: expected values from GNU `date -u -d … +%s` -/

#guard parseTs "2026-10-20T03:55:09Z" == some 1792468509
#guard parseTs "1970-01-01T00:00:00Z" == some 0
#guard parseTs "2000-02-29T23:59:59Z" == some 951868799
#guard parseTs "2000-03-01T00:00:00Z" == some 951868800
#guard parseTs "2024-12-31T23:59:59Z" == some 1735689599
#guard parseTs "9999-12-31T23:59:59Z" == some 253402300799

And because main returns a value, the whole program can be tested in hand-built worlds, with no network and no mocking framework:

/-- A world whose GET returns `body` and whose POST returns `postResult`.
The POST stub returns a *fixed* answer, not one derived from the request,
so it can't accidentally agree with the code under test. -/
def worldWith (body : String) (postResult : PostResult) : World :=
  { get := fun _ => .response 200 body, zone := fun _ => ⟨-18000, "CDT"⟩,
    now := 1792468509 + 300, post := fun _ => postResult }

#eval do
  let body ← fx "site3963"
  let posts (argv : List String) (pr : PostResult) :=
    ((main argv).run (worldWith body pr)).1.filter Event.isPost |>.length
  let exitOf (argv : List String) (pr : PostResult) := ((main argv).run (worldWith body pr)).2
  -- at / above / below threshold (level is 677.58)
  check "alert at equal" (posts ["--threshold", "677.58"] (.response 200) == 1)
  check "alert below"    (posts ["--threshold", "600"] (.response 200) == 1)
  check "no alert above" (posts ["--threshold", "677.59"] (.response 200) == 0)
  check "no threshold"   (posts [] (.response 200) == 0)
  -- R62, with known-wrong worlds injected: every failed delivery must exit non-zero
  check "delivered → 0"  (exitOf ["--threshold", "600"] (.response 200) == 0)
  check "HTTP 500 → 1"   (exitOf ["--threshold", "600"] (.response 500) == 1)
  check "HTTP 302 → 1"   (exitOf ["--threshold", "600"] (.response 302) == 1)
  check "network → 1"    (exitOf ["--threshold", "600"] (.failed "timeout") == 1)
  check "usage → 2"      (exitOf ["--threshold", "nan"] (.response 200) == 2)

Note the stub's design. The fake POST returns a fixed result chosen by the test, never one computed from the request. A stub that derived its answer from what the code sent could end up agreeing with a bug.

The fixtures in test/fixtures/ are a real API response, trimmed, plus doctored copies: a null value, a timestamp with a +00:00 offset, the impossible date 2026-02-29, the wrong site number, a tie for newest, and so on.

What we have, and what we don't

$ lake env lean scripts/Audit.lean
theorems proved from standard axioms only: 0
theorems still depending on sorry: 48
definitions still depending on sorry: 0

Every test passes, and every definition is real. But a test is a "there exists" claim: there are inputs on which it works. Every obligation in Proofs/ is a "for all" claim. The tests check parseTs on 22 strings; parseTs_spec covers every string. The tests check three HTTP statuses and one network failure for the alert; never_silently_fails covers all of them, in every combination with every response body, clock and time zone.

Process note

Neither the tests nor, later, the proofs found a bug in this implementation. That's normal. The code was written carefully against a precise spec, with the proofs in mind. Most of the bug-finding happened earlier, in Stage 1, before any code existed. What the proofs add (next lesson) is the step from "we looked hard and found nothing" to "no input can cause this".

Try it

Plant a bug yourself. Change (2 * N + D) to (2 * N + D - 1) in roundFrac, run lake build Tests, and see which test catches it. Then put it back. (Building Tests also builds the proofs, so a proof will fail too. To see only the tests, build at stage-4, where the proofs are still sorry.)
