The model: the design before the code

Stage 2 turns the requirements into mathematical objects. They're written in ordinary maths notation, so the ideas are visible before any Lean syntax gets in the way. Stage 2 also makes three design decisions that the rest of the project depends on.

Stage 2 commit 2a253c8 what changed since stage-1 docs/02-formal-model.md

Idea 1: a spec must not be a copy of the code

Suppose the spec for rounding were "the result is (2N + D) / (2D)", which happens to be the formula the implementation uses. Then the proof that the implementation meets the spec is trivial, and it tells you nothing: if the formula is wrong, the spec is wrong in exactly the same way.

C++ analogy

It's the formal version of a test mistake you've probably seen: the expected value in the test was computed by calling the function under test, or by copy-pasting its logic. The test can never fail. A spec that restates the algorithm has the same problem.

So every spec in this project is written in a different style from the code it constrains:

StyleExample hereThe implementation instead…
Relational: says when an answer is acceptablerounding: "k is within ½ of x; ties go away from zero"uses integer division
Characterization: rules that only one function satisfiescalendar: "day(1970-01-01) = 0, and day(tomorrow) = day(today) + 1"uses a closed-form formula with divisions by 4, 100, 400, 153 and 146097
Inverse: round triptimestamp parsing: parse(s) = t exactly when s is the rendering of a real date that denotes tpattern-matches 20 characters
Declarative: describes the answer, not the search"the reading at some index i, with nothing later, and everything before i strictly earlier"is a loop that keeps the best reading so far
Whole-run properties: about everything the tool does, whatever the network, clock and time zone do"never exit 0 having failed to alert"is the whole tool (Idea 3 shows how this can be stated)
Template (the fallback)the exact text of the reportis that template. Checked against the PRD's examples, not proved meaningful.

The calendar one is worth a second look. The spec never mentions leap years in a formula. It only uses "tomorrow", which is easy to define obviously correctly: if the day is less than the number of days in the month, add one; otherwise go to the first of the next month; after December, go to the next year. Any function that starts at 0 on 1 January 1970 and goes up by exactly one every "tomorrow" is the day count. There's only one such function.

Nothing protects you from triviality

It's easy to assume that working formally keeps you safe from a tautological spec. It doesn't. A spec that repeats the implementation's algorithm passes every check in this project:

  • it type-checks;
  • its proofs go through, often more easily than proofs against an independent spec;
  • the audit from Lesson 1 reports every theorem proved, using only the standard axioms;
  • the planted-bug checks of Lesson 10 still pass. Change the implementation and a proof against a copied spec breaks, exactly as a proof against a good spec would.

Nothing turns red. The only protection is a person deciding, for each spec, that it describes the answer differently from how the code computes it, and a second person checking that decision.

How this project keeps them different

Since no tool can tell you that a spec restates the code, the project relies on three habits instead:

  • The spec was written first. Stage 3 writes the whole spec before Stage 4 writes any implementation, so there was no code to copy.
  • Ask how you would recognize a correct answer. When you can't think of a second way to describe something, ask how you would recognize a correct answer without computing it. Checking an answer is often much simpler than producing one: "within ½ of x, ties away from zero" is easier to state than the integer division that achieves it.
  • Check some of the spec against answers from outside. For some specs, such as rounding, a theorem proves that the spec allows exactly one answer. The tests compare the implementation with values taken from outside the code (the PRD's examples, GNU date). The implementation meets the spec, the spec allows one answer, and that answer matches the outside value, so on those examples the spec is right. Away from the examples, a spec and an implementation that make the same mistake still agree.

Noticing that a spec and its implementation use the same technique is left to a reviewer who didn't write the code and who reads the spec against the requirements. When no independent description can be found, the result is the Template row in the table: the spec is the code, and the tests use expected values from somewhere else.

Idea 2: a pure core and a thin shell

You can prove things about a function from inputs to outputs. You can't prove much about "whatever the network does next". Lesson 3's tags already pointed at this: the requirements tagged Proved must live in code that does no I/O at all. So the tool is split in two:

  • a pure core, which never performs I/O. Everything it needs from the outside world comes in as arguments, and everything it produces goes out as return values;
  • a shell, which performs the I/O and calls the core.

The pattern is called functional core, imperative shell. It's worth using even without proofs, because the core becomes easy to unit-test.

Lean enforces the split for you. A Lean function that performs I/O has to say so in its type: it returns an IO value. A function whose type doesn't mention IO can't perform I/O (apart from debug tracing and deliberately unsafe escape hatches), so the compiler checks that the core stays pure. Haskell works the same way, if you're familiar with it. In other languages, you can follow the pattern by discipline instead.

The most direct way to apply the pattern to lake-level would be a shell like this sketch, which calls pure functions for every computation:

main(argv):
  cfg      = parseArgs(argv)                  # pure
  response = httpGet(fetchRequest(cfg))       # I/O
  reading  = decode(response)                 # pure
  print(report(reading))                      # I/O
  if shouldAlert(cfg, reading):               # pure
    status = httpPost(alertRequest(cfg, reading))   # I/O
    if status is not 2xx:
      exit 1
  exit 0

Every function the shell calls could be proved. But look at what the shell itself still decides: what to fetch first, that the report is printed before the alert is sent, and that a failed alert means exit 1. That last line is R62, "never exit 0 having failed to alert", the requirement Lesson 1 called the most important in the project. In this sketch it's a line of shell code, and no theorem covers it.

Idea 3: the computation itself is a value

In the sketch above, the shell is in charge. The tool is mostly unproven code with small proven pieces set into it, like gems in clay.

lake-level proves more of the code by reversing that relationship. The part in charge is the pure core: it makes every decision, including the R62 one, and the proofs cover all of them. What's left unproven is a thin outer layer that carries out the core's requests and decides nothing, plus a few trusted components the core relies on from inside, such as the JSON parser. The tool is mostly proven code, with a few unproven pieces inside it and a thin unproven layer around it, like a diamond with small inclusions.

In lake-level, the core is about 450 lines and makes every decision. The shell is 80 lines and makes none. Lesson 12 is about that outer layer and those inclusions.

How the core stays in charge without doing I/O

The core can't perform I/O, so it can't make the request and then decide what to do with the answer. Instead, it returns a description of the whole computation, as a value of type Prog. (Prog is short for "program", but in these lessons it always means this value, never the lake-level tool as a whole.)

A Prog is a chain of steps. Each step either asks the outside world one question (fetch this URL, what time is it), prints some text, or ends the run. The chain doesn't exist in advance. When the core returns, only the first step exists, along with a function that will compute the next step once the first one's answer is known. Every later step works the same way.

The answers come from the world: whoever replies to the HTTP request, the system clock, the time-zone database. This is the same "world" as in Lesson 1's theorem, which held for every possible world. The world supplies one operation for each kind of question. An executor works through the chain. It takes the current step, gets the answer from the world, and calls the step's next function with it to get the following step.

So each step is split in two. The world supplies how to answer the question, and the step supplies what to do with the answer:

StepThe step holdsThe world suppliesIn lake-level, next…

(A → B is the type of a function that takes an A and returns a B.) Whatever the world produces is exactly what that step's next takes: an httpGet's next takes a GetResult, a clock's takes an Instant, and so on. None of the steps receives an answer directly. The answer goes into next, which is ordinary pure code in the core, and next decides which step comes after. The types are:

  • Request: an HTTP method, URL, headers and body, as plain data.
  • GetResult: either response(status, body), or failed(message) if no response came back (curl couldn't connect, or timed out).
  • PostResult: response(status) or failed(message).
  • Instant: a time, in seconds since 1970-01-01 UTC.
  • Zone: a UTC offset and an abbreviation, such as CDT.

A function like next, which receives the result of a step and says what to do after it, is called a continuation.

The split is deliberate. Every decision lake-level makes lives in the steps, and everything outside its control lives in the world. The core can't know what a server will send back, so it doesn't pretend to. It only says what to do with each possible answer. The R62 decision from the sketch is now in the next of the httpPost step: given a failed POST, it returns an err step that prints an error and ends with exit 1.

Taken together, the four operations make up a world:

World = ( get  : Request → GetResult,
          now  : Instant,
          zone : Instant → Zone,
          post : Request → PostResult )

Why bother

When you run lake-level for real, the world is the actual network, clock and time-zone database, and the executor is the shell in Main.lean. But nothing about a Prog requires that. Any four functions with the right types make up a world, and a Prog can be run against any of them.

Lean's own IO type couldn't do this. An IO value is opaque: Lean can run it, but nothing can look inside it or run it against a different world, so there'd be nothing to state theorems about. A Prog is ordinary data, so it can be run against any world, including one made up for a proof.

Running a Prog against a world produces a trace, which is the list of events an observer would see (a GET, some output, a POST, and so on), and an exit status. Properties of the whole tool then become ordinary statements about functions, and they can be stated for every world:

RequirementProperty of run(main(argv), W), for all argv and all W
R3a usage error ⇒ the trace contains no GET and no POST
R15the response is invalid ⇒ no output, no POST, exit 1
R50the trace contains a POST ⇔ a threshold was given ∧ the response is valid ∧ level ≥ threshold
R52every POST comes after an output
R62threshold given ∧ level ≥ threshold ∧ the POST failed ⇒ exit ≠ 0

(main is the core's entry point: it takes the command line and returns the first step.)

A world plays the part of a mock in a unit test. A test might use one mock that returns HTTP 500 and check that the exit code is 1. A theorem "for every W" covers every possible mock at once: every status code, every response body, every clock reading, every combination. That's why requirements which Stage 1 could only tag as Inspected, such as R52 ("every POST comes after an output"), become Proved here. In the mostly-unprovable sketch from Idea 2, R52 was the order of two lines in the shell.

In Lean

Here's how it eventually looks in Lean, in the spec layer. Lesson 5 covers the syntax. For now: an inductive is a tagged union, k is the continuation (next above), and Nat is a non-negative whole number. The Lean names for httpGet and httpPost are get and post.

inductive Prog where
  | done (exit : Nat)
  | get (req : Request) (k : GetResult → Prog)
  | zoneAt (t : Instant) (k : Zone → Prog)
  | clock (k : Instant → Prog)
  | out (s : String) (k : Prog)
  | err (s : String) (k : Prog)
  | post (req : Request) (k : PostResult → Prog)

/-- Every possible environment. Each kind of question is asked at most once
per run, so a function per question loses no generality. -/
structure World where
  get : Request → GetResult
  zone : Instant → Zone
  now : Instant
  post : Request → PostResult
About the symbols

Lean code really is written with Unicode symbols such as →, ∀, ∧, ≤ and ⟨ ⟩. Lean's own standard library uses them tens of thousands of times, and Lean prints them in every goal and error message. Nobody types them from a character map: the official Lean extension for VS Code replaces a backslash abbreviation as you type, so \to becomes →, \and becomes ∧, \le becomes ≤, and \< and \> become ⟨ and ⟩. Most of the symbols also have an ASCII spelling that Lean accepts, such as -> for → and forall for ∀, but you'll rarely see it in real Lean code.

Prog.run is the mathematical executor. For each step, it feeds the world's answer to the continuation, records the event, and keeps going:

/-- The meaning of a `Prog` in world `w`: the trace of events and the exit status. -/
def Prog.run (p : Prog) (w : World) : List Event × Nat :=
  match p with
  | .done e => ([], e)
  | .get r k => let x := (k (w.get r)).run w; (.get r :: x.1, x.2)
  | .zoneAt t k => let x := (k (w.zone t)).run w; (.zone t :: x.1, x.2)
  | .clock k => let x := (k w.now).run w; (.clock :: x.1, x.2)
  | .out s k => let x := k.run w; (.out s :: x.1, x.2)
  | .err s k => let x := k.run w; (.err s :: x.1, x.2)
  | .post r k => let x := (k (w.post r)).run w; (.post r :: x.1, x.2)

The rest of the model

docs/02-formal-model.md also defines:

  • Exact decimals: a pair ⟨m, e⟩ meaning m / 10e. So 677.58 is ⟨67758, 2⟩. This happens to be exactly how Lean's JSON parser stores numbers, so nothing is ever converted to binary floating point.
  • Time: civil dates, instants as seconds since 1970, the timestamp round trip, and the 12-hour clock.
  • Valid responses and the declarative latest reading.
  • What the model leaves out on purpose: the JSON parser, curl, the time-zone database, the clock, the compiler, and Lean's kernel. Writing that list down at this stage, before any code, is what makes Stage 6's list of assumptions possible.
Process note

The model is in maths notation first, not Lean, on purpose. The three design decisions (spec independence, a pure core, the computation as a value) are easier to argue about on paper than in code. They also turn out to be the decisions everything later depends on. The whole-tool theorems of Lesson 8 exist only because Prog is decided here.

Try it

Pick a function in your codebase that does I/O and makes a decision (retries, alerting, failover). Write it as a chain of steps: what questions does it ask the world, and what does it do with each answer? Then write down one property that should hold for every possible sequence of answers.
