Lesson 13

Behind the scenes: how this was actually built

This lesson describes how the repository was actually built: the order things really happened in, the dead ends, how the proofs were split across parallel workers, and the mistakes the checks caught. The work was less orderly than the stage commits make it look.

Who built it

This repository was built by an AI coding agent (Claude, working in Claude Code), directed by the repository's owner, who asked for a toy project to learn formal verification from: "start with an English-prose PRD … and formalize it progressively", in a language of the agent's choosing, "as formally verifiable as is realistically possible". The choice of Lean, the stages, and the techniques were the agent's. Everything below comes from that working session.

That matters for how much you should trust it, and the answer is the same as for human-written proofs. You don't need to trust whoever wrote the proofs, because the kernel checks them (Lesson 1). You do need to read the theorem statements and the trusted base yourself, because nothing checks those for you.

A few working rules, set up front

The session ran under some standing rules that shaped a lot of what you've seen:

  • Verify, never recall. Every claim about the original program's behavior was checked by running it. Every claim on these pages about the binary, the generated C or the error messages was re-run while writing them.
  • Stubs must never agree with the thing under test. Hence the fixed-answer worldWith in the tests, the fake curl pinned to a contract test, and expected values from GNU date instead of from the code.
  • Inject known-wrong values to prove a check can fire. Hence every mutation table in Lesson 10.
  • When a bug is found, sweep for its whole class. When one "zero calls" check turned out to be vacuous, every negative assertion got a positive control.
  • State plainly what a test can't cover. Hence "what is still not covered" in Lesson 12.
  • Confirm before outward-facing actions. Hence no real alert was ever sent to ntfy.sh: that publishes to a public topic.

The real timeline

Setup

Lean was installed with elan into the user's home directory, without editing their shell profile. The decision to use Lean core only, no Mathlib (Lean's large maths library) came early: the build takes seconds instead of a long first download and compile, and less code means a smaller trusted base. The cost showed up later, when several familiar tools turned out to be Mathlib-only.

Stages 0–2: documents, checked against reality

The PRD came first. For Stage 1, every ambiguity was checked against the original by running it: Python's float("nan"), argparse accepting --thr as an abbreviation, and so on. The live API was sampled too: 4,306 records, all in the same UTC format, and an unknown site number that returns HTTP 200 with an empty list rather than a 404. Stage 2's model was written in ordinary maths notation.

Stage 3: the spec meets the type checker

Writing the spec in Lean produced a series of small errors:

  • List.Forall₂ ("these two lists correspond element by element") is in Mathlib, not core. ValidResp was rewritten with equal lengths plus a condition at each index, which turned out to be clearer anyway.
  • {1,64} inside a Lean s!"…" string was read as interpolation. Escaped as \{1,64} (you can see it in Impl/Args.lean).
  • The audit's first draft reported "87 proved" with nothing proved (Lesson 6). Fixed before the commit.

Stage 4: implementation and tests

Each implementation choice was made with the coming proofs in mind, especially the closed-form calendar. Before committing, four bugs were planted to show the tests could fail.

Stage 5: proofs, in parallel

Before handing anything out, the hardest technique was prototyped in a scratch file: inverting the calendar formula with "monotone plus 400 checked endpoints" (Lesson 9). Once that was known to work, the proofs were split across four parallel sub-agents, each in its own git worktree based on stage-4:

WorkerAssignment
1Proofs/Decimal.lean: 10 theorems (comparison, rounding, parsing, rendering)
2Proofs/Calendar.lean: 8 theorems (day count, instants, timestamp parser, 12-hour clock)
3Proofs/Select.lean and Proofs/Decode.lean: 5 theorems
4Proofs/Args.lean and Proofs/Render.lean: 13 theorems
main sessionProofs/Program.lean: the whole-program theorems, including never_silently_fails

Each worker got the same rules. Here are three of them, from the calendar worker's instructions:

- Do NOT change theorem statements, anything in LakeLevel/Spec/, LakeLevel/Types.lean,
  LakeLevel.lean, or other Proofs files. If a statement is false or unprovable as written,
  stop on that theorem and report the exact counterexample/reason and a proposed minimal
  fix — do not apply it.
- You MAY restructure an Impl function in LakeLevel/Impl/Calendar.lean only if behavior is
  unchanged and it's needed for provability; `lake build` (which runs test/Tests.lean) must
  still pass, and you must list every such change in your report.
- Forbidden: sorry, admit, native_decide, `decide +native`, new axioms, Mathlib/Batteries.

(Three of the rules, with lines re-wrapped for width. The last one goes on to list the tactics that were allowed, such as decide +kernel and omega.) The first rule is the important one. A worker under pressure to make a proof go through can weaken the statement until it's provable, and a weaker statement is a weaker guarantee. So statements were off limits to workers. Only the main session could change one, and only after reviewing the reason.

Merging the workers' results

Each worker reported back with a commit. The merges weren't automatic; each one was read:

  • The decimal worker reported unused hypotheses (1 ≤ n on three rendering theorems). As instructed, it didn't change the statements; it reported them. The main session removed the hypotheses, which strengthened the theorems (Lesson 9).
  • The args worker deleted theorem doc comments while restructuring its file. They were restored from stage-4. Harmless for correctness, but doc comments are where the theorems explain themselves to reviewers, so they matter.
  • The decode worker refactored decode into named steps. That was permitted, since behavior was unchanged and the tests still passed (Lesson 9).
  • Two workers independently hit the omega-ignores-Instant surprise.

Meanwhile the main session's own proofs hit their own snags. split wouldn't split an if buried inside a list, so it was replaced by an explicit by_cases on cfg.json. :: binds tighter than ++, so a :: b ++ c isn't what it looks like, and a rewrite lemma (List.cons_append) was needed. Some lemma names were deprecated (if_true, replaced by ite_true). And tauto, a standard tactic for propositional logic, is another Mathlib-only tool.

Before the worker branches were deleted, each was confirmed, file by file, to be fully contained in the merged result.

Stages 5 and 6 overlapped, then were split

While the workers were proving theorems, the main session wrote the shell and the end-to-end tests. So for a while the working copy held both stages' changes at once. They were committed separately, so that each commit shows one stage. The stage-5 commit used a lakefile.toml without the executable target, and left out the shell and its tests. Then each tag was checked out fresh and built from scratch, to show it stands on its own: stage-5 builds and audits 48/48, and stage-6 passes every check.

Stage 6: the checks find problems in the checks

  • The e2e call counter's glob was wrong, making every "no POST" check vacuous. Found by a positive control (Lesson 10).
  • The curl contract test's own harness had a bug capturing exit codes, because curl's output with these flags has no trailing newline. It was caught because the check failed on behavior that was actually correct, and the harness was fixed rather than the expectation.
  • Planting "reject responses without siteNumber" passed every test and broke a proof. A new fixture was added (Lesson 10).

Writing these lessons

Writing a lesson is another review, and it found things too:

  • Reading the theorem statements against the requirements while writing Lesson 6 showed that parseArgs_dup is narrower than requirement A20.
  • The first attempt at re-running the audit's negative test edited the obligation list as well, and so "passed" (Lesson 10).
  • Every excerpt on these pages is machine-checked against the repository (scripts/check-lessons.py), and that checker was itself given known-wrong excerpts before being trusted.

What the process says about the method

Look at where problems were actually found:

Found by…What
trying to write requirements (Stage 1)the NaN threshold bug, string-compared timestamps, URL injection, float rounding
the type checker (Stage 3)missing index-bound proofs; an under-specified correspondence between records and readings
planting bugsa test gap (missing siteNumber); a vacuous test; an audit that couldn't see deletions
the proofs (Stage 5)an over-weak spec (unused hypotheses); no implementation bugs
running both programs side by side (Stage 6)an error in the Stage 1 analysis
reading statements against requirementsa theorem narrower than its requirement

The proofs themselves found no bugs in the implementation. That's the typical pattern. By the time you can state a theorem precisely, you've usually already found the bugs, because stating it precisely is where they show up. What the proofs add is a guarantee that no bugs of those kinds are left, for any input. They also keep that true through future changes, because a change that breaks a proof doesn't build.
