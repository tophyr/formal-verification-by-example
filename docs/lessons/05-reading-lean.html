Lesson 5

Reading Lean, for C++ programmers

Just enough Lean 4 to read every file in this repository. You won't be able to write proofs after this lesson, but you'll be able to read a theorem and tell what it claims, which is the more important skill.

Lean 4 is two things at once: a functional programming language that compiles to native code, and a proof assistant. Every example below is real code from the repository at stage-6, and the caption on each one links to it.

Data: structure and inductive

A structure is a struct:

/-- An exact decimal `m / 10^e`. Deliberately the same shape as Lean's
`JsonNumber`, so JSON numbers convert without rounding (A3, R16). -/
structure Dec where
  m : Int
  e : Nat
  deriving Repr, DecidableEq, Inhabited

/-- … -/ is a doc comment, -- is a line comment. deriving asks the compiler to generate code: Repr is printing, DecidableEq is operator==, Inhabited is a default value.

Int is the integers (…, −2, −1, 0, 1, 2, …), and Nat is the natural numbers (0, 1, 2, …): whole numbers that can't be negative. Neither has fractions; that's Rat, in the table below. So m can be negative (−1.25 is ⟨-125, 2⟩), but e, the number of decimal places, can't, and the type says so: nothing has to check or prove that e is at least 0. Both are arbitrary precision. There's no overflow anywhere in this project, which removes a whole class of things to prove.

An inductive type is a tagged union, like std::variant with named alternatives that each carry their own fields:

/-- What the world answers to a GET. -/
inductive GetResult where
  | response (status : Nat) (body : String)
  | failed (msg : String)
  deriving Repr, DecidableEq

Each line starting with | is one alternative, called a constructor. Each group in parentheses after a constructor's name is one field, written (name : Type). So response carries two fields, a status that is a Nat and a body that is a String, while failed carries one, a msg. In C++ terms, response is roughly a struct { unsigned status; std::string body; }, and a GetResult holds either a response or a failed. Lean writes each field or parameter in its own parentheses, separated by spaces, not commas. Functions use the same notation, as the next section shows. Building a value works the same way: .response 200 "…" is a GetResult with status 200 and that body.

Lean's standard library defines more types the same way. Option, Except and List are themselves inductive types, and Array, pairs and Rat are structures. You'll see them as the types of fields, arguments and results: select, for example, takes a List Reading and returns an Option Reading. In this table, α, β and ε stand for any type, like T in a C++ template:

Functions

/-- Keep the first reading seen with the latest instant: replace only on *strictly* later. -/
def select (rs : List Reading) : Option Reading :=
  match rs with
  | [] => none
  | r :: rest => some (rest.foldl (fun best x => if best.t < x.t then x else best) r)

Reading it:

  • def select (rs : List Reading) : Option Reading := declares a function that takes a list of readings, named rs, and returns an optional reading. The type after the parameters is the result type, and := means "is defined as": what follows is the body.
  • match rs with and the | lines below it are pattern matching on rs: the empty list gives none; a list with first element r and the rest rest gives some (…). The compiler rejects the match if a case is missing.
  • rest.foldl f r is std::accumulate(rest.begin(), rest.end(), r, f).
  • fun best x => … is a lambda: [](auto best, auto x) { … }.
  • Function application is by juxtaposition: f x y, not f(x, y). Parentheses are only for grouping.

In C++:

std::optional<Reading> select(std::list<Reading> const& rs) {
  if (rs.empty()) return std::nullopt;
  return std::accumulate(std::next(rs.begin()), rs.end(), rs.front(),
      [](Reading const& best, Reading const& x) { return best.t < x.t ? x : best; });
}

Several parameters

select has one parameter. A function with several lists them one after another, each in its own parentheses, like the fields of GetResult above:

/-- Round `N / D` to an integer, ties away from zero: for `N ≥ 0`,
`⌊(N + D/2) / D⌋ = ⌊(2N + D) / 2D⌋`; mirrored for `N < 0`. -/
def roundFrac (N : Int) (D : Nat) : Int :=
  if 0 ≤ N then (2 * N + D) / (2 * D)
  else -((2 * (-N) + D) / (2 * D))

/-- Round `d` to `n` places: the rounding of `d.m·10ⁿ / 10^d.e`. -/
def Dec.round (n : Nat) (d : Dec) : Int :=
  roundFrac (d.m * ((10 ^ n : Nat) : Int)) (10 ^ d.e)
  • roundFrac takes an Int called N and a Nat called D, and returns an Int: roughly Int roundFrac(Int N, Nat D) in C++.
  • Calls work the same way, with arguments separated by spaces: roundFrac 5 2 is 3 (2.5, rounded away from zero). Dec.round calls it with two arguments, and each parenthesized expression, (d.m * …) and (10 ^ d.e), is one of them.
  • Written with arrows, Dec.round's type is Nat → Dec → Int: one arrow per parameter, and the last type is the result. Lean shows types this way in its messages, and Lesson 6 uses it for a function passed as an argument.

Pure, and total

Lean functions can't mutate anything or do I/O (except inside the IO type, which only Main.lean uses). They also have to be total: every case handled, and every call guaranteed to terminate. The compiler checks both. Code that can't be shown to terminate must be marked partial, and then you can't prove anything about it. In this repository exactly one function is partial: the shell's interpreter loop in Main.lean, which is outside the proofs anyway.

You'll also see do blocks with ← and let. They look imperative, but they're syntax for chaining Option/Except steps: let x ← step means "run step; if it failed, return the failure now; otherwise call the result x". It's like a chain of early returns on std::expected.

Statements: Prop versus Bool

This is the first real difference from C++. A Bool is a runtime value, true or false. A Prop is a statement, which might be true or false and which you might be able to prove. 2 + 2 = 4 is a Prop. So is "every list has a latest reading", which you can't compute but can prove.

/-- HTTP success. -/
def ok2xx (status : Nat) : Prop := 200 ≤ status ∧ status < 300

instance (s : Nat) : Decidable (ok2xx s) := by unfold ok2xx; infer_instance

/-- The world delivered this POST. -/
def Delivered (w : World) (q : Request) : Prop :=
  ∃ status, w.post q = .response status ∧ ok2xx status

ok2xx is a statement about a status code. The instance … Decidable line says it can also be computed, so the program may use if ok2xx st then …. Delivered says "there exists a status such that the world answered the POST with that status, and it's 2xx". It's never computed; it only appears in theorems.

Specs are written as Props so they can say things code can't, like "for every list" or "there exists an index". The implementation is written with Bools so it can run. Compare the spec of a decimal's value with the implementation of comparison:

/-- The rational number a `Dec` denotes: `m / 10^e`. All semantics go through this. -/
def Dec.val (d : Dec) : Rat := (d.m : Rat) / ((10 ^ d.e : Nat) : Rat)
/-- Exact comparison `a ≤ b`, by cross-multiplying: `a.m·10^b.e ≤ b.m·10^a.e`. -/
def Dec.le (a b : Dec) : Bool :=
  decide (a.m * ((10 ^ b.e : Nat) : Int) ≤ b.m * ((10 ^ a.e : Nat) : Int))

((x : Rat) is a cast, like static_cast<Rat>(x).)

Theorems are functions

Here's the theorem connecting those two:

/-- Comparison is exactly rational `≤`. -/
theorem Dec.le_iff (a b : Dec) : Dec.le a b = true ↔ a.val ≤ b.val := Dec.le_iff' a b

Read it as a function declaration, because that's literally what it is:

  • the name is Dec.le_iff;
  • the parameters are (a b : Dec). Any two decimals: the parameters are where "for all" comes from;
  • the return type is the statement: Dec.le a b = true ↔ a.val ≤ b.val, "the code says ≤ if and only if the true rational values are ≤";
  • the body, after :=, is the proof. Here it's just a call to a helper theorem Dec.le_iff' that does the real work.

A proof of "A implies B" is a function that takes a proof of A and returns a proof of B. A hypothesis is just a parameter whose type is a statement. In the headline theorem from Lesson 1, (h0 : exitCode argv w = 0) is a parameter: you can only call the theorem if you can hand it evidence that the exit code was 0.

So "the theorem is proved" means "this function type-checks". The type checker (the kernel) is the proof checker. (This correspondence between propositions and types, and proofs and programs, is called the Curry–Howard correspondence. You don't need the theory; you just need to know why a proof checker can look like a compiler.)

Tactics: writing a proof interactively

Writing out a whole proof by hand, as a term, gets tedious quickly. Instead, most proofs are written in tactic mode, entered with by. You see the current goal (what's left to prove), and each tactic transforms it, until nothing is left. It's like a debugger session where you step a proof instead of a program.

/-- … and only fails on an empty list. -/
theorem select_none_iff (rs : List Reading) : select rs = none ↔ rs = [] := by
  cases rs <;> simp [select]

This is what Lean shows you (in an editor, it appears in a side panel as you move the cursor). At the start, above the line are the things you have; below ⊢ is what you must prove:

rs : List Reading
⊢ select rs = none ↔ rs = []

cases rs splits on the two shapes a list can have, leaving two goals:

case nil
⊢ select [] = none ↔ [] = []

case cons
head✝ : Reading
tail✝ : List Reading
⊢ select (head✝ :: tail✝) = none ↔ head✝ :: tail✝ = []

<;> means "then run the next tactic on every resulting goal". simp [select] unfolds the definition of select and simplifies: in the first case both sides are true; in the second, both sides are false (some … is never none, and a non-empty list is never []). No goals remain, so the proof is done. (The ✝ marks names Lean made up, which you can't refer to.)

The tactics you'll see most in this repository:

TacticWhat it does
intro hto prove "A → B", assume A (call it h) and prove B
exact e"here is exactly the thing you asked for"
cases x / rcases / obtain ⟨a, b⟩ := hsplit into one goal per shape of x; take apart an "and" or "exists"
by_cases h : Ptwo goals: one where P is true, one where it's false
inductionprove it for the empty case and for "one more", like a recursive function
unfold f / simp [f]replace f by its definition / rewrite and simplify with known facts
rw [h]rewrite using an equation h : a = b: replace a by b
omegaa decision procedure: proves any true linear-arithmetic fact about integers (with +, * by constants, / and % by constants)
decideevaluates a statement that's decidable and finite, and checks it's true
refine ⟨?_, ?_⟩"I'll build this pair; give me a goal for each hole"
constructorsplit an "and" or "if and only if" into its parts

sorry: the placeholder

sorry closes any goal without proving it. The compiler accepts it with a warning. It's how you write a theorem's statement before its proof, the way you might write throw std::logic_error("TODO"). Anything built on sorry is marked as depending on the axiom sorryAx, which is how the audit finds it. In Stage 3, every proof in the repository was sorry.
